# Desktop caches, logs, and old test output

Include these desktop/system categories in the normal cleanup audit, even when they are unrelated to MAKO. Examples are discovery locations, not deletion patterns. Resolve the current installation, XDG paths and Flatpak app IDs; do not reuse old measurements or assume that previously deleted folders have stayed empty. Honor current user exclusions and retained runtime versions. Broad discovery still requires a measured, approved removal set; it does not authorize wiping application profiles or system directories.

## Candidate map

Explain the reindexing cost. Identify it as shared editor cache in the approval plan because it may cover projects outside MAKO. |

| Browser web cache | Firefox profile `cache2` under the native/Flatpak cache root | Clear through the browser where practical, or remove exact cache paths after shutdown. Preserve profiles, cookies, passwords, history, session recovery and site data. | Rotated application/service logs | Steam `logs/*.previous.txt`, dated app logs, Decky logs, Codex/Claude/Kimi app logs, XDG state roots, and rotated/compressed service logs under `/var/log` | Enumerate exact files and verify the owner; preserve active logs and evidence still needed for investigation. Prioritize meaningful savings while including small logs in the inventory. Package-manager caches, compiler/package caches, Steam shader caches, game prefixes, emulator environments and Flatpak SDKs are not blanket cleanup targets. Distinguish superseded downloaded installers from installed runtimes, user data, and essential reusable tooling. Use supported owner commands for specifically approved package maintenance and preserve the skill's protected Flatpak/build caches.

## Journal maintenance

Use read-only `journalctl --disk-usage` and journal metadata for the intended system/user/directory/namespace scope. Do not read or publish unrelated log contents. Distinguish disk-backed persistent journals from volatile tmpfs journals. The usage total includes active files and is not a guaranteed reclaimable estimate. Verify maintenance scope from the installed help/man page and the selected journal directory or namespace; do not assume query filters for units, boots, dates, or users constrain vacuuming.

When there is worthwhile archived history to reclaim, propose an explicit scope and bounded `journalctl --vacuum-size=…` or `--vacuum-time=…` operation supported by the installed version. Show the selected retention value and loss of older diagnostics in the approval plan; choose it from current debugging needs, not a universal zero-history policy. Vacuuming affects archived journal files, so retained active files can keep total usage above the requested size. Do not remove journal directories, force rotation, truncate live files, or change persistent journald/logrotate settings as an incidental cleanup step. If rotation is needed for an authorized maintenance goal, disclose it in that plan before execution.

Execute only the approved scoped owner command, using administrator authentication if required, then remeasure. A retention-bound operation is not an exact static file list: report the owner-reported deletion and observed disk change instead of promising the entire journal total.

## Before removing files

Build the normal exact-path manifest with measured allocated bytes and protected paths. Keep repository/test output, application caches, logs, crash reports, and installer backups as separate categories so the user can approve or exclude them independently. Do not count an entire mixed task folder as disposable merely because most of it is generated.

For application caches and databases, use the owner’s cache-clear action or have the user save work and close the app. Recheck immediately before deletion: an app can restart between checks. Inspect host processes, open descriptors, executable paths and mapped libraries, rather than only the sandbox’s process view. If an app remains active, skip its dependent cache and complete independent targets. Do not kill apps or unsaved sessions as an automatic cleanup step; a normal shutdown of a residual process requires user authorization.

For old test trees, check current repository/history references and consumers as well as process inactivity. Inspect nested repositories, dependency downloads, licensed/model payloads and source patches. Prefer removing verified generated children over deleting the whole task directory. Report that removed test results lose local historical measurements and removed build trees will need recompilation.

Closed or completed files still need path, symlink, mount and fingerprint checks from the main skill. Take inventory once and revalidate the selected exact files; do not expand a wildcard deletion while the application is creating new files.

## Administrator authentication and completion

Use ordinary execution approval for paths outside the workspace. Protected system crash dumps may also require OS administrator authentication. If passwordless sudo is unavailable, use an installed desktop authentication mechanism such as `pkexec` for the same bounded, approved operation, when supported. Tell the user where to authenticate; never request a password in chat. Keep unrelated privileged paths out of the operation. If authentication is unavailable or cancelled, report that precise blocker and finish user-owned cleanup without escalating the scope.

Verify selected targets were removed and protected app/profile/source paths remain. Separate measured removed bytes from observed free-space change. Deleted files held open by a process can retain space until it exits; report that condition instead of killing processes or repeatedly deleting paths. Do not count tmpfs or remote-storage savings as local SSD savings. Do not rebuild/repopulate caches to validate cleanup or change cache limits/retention settings unless requested.
