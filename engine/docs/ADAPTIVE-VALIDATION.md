# Adaptive validation

Adaptive Frame Generation needs two kinds of evidence: deterministic policy tests for scheduler decisions, and real Vulkan tests for drivers, presentation, Gamescope, GPU work, and game behavior. Passing one does not substitute for the other.

## Portable policy tests

From `engine/`, run:

```bash
scripts/test-adaptive-scheduler.sh
MAKO_ENABLE_SANITIZERS=ON scripts/test-adaptive-scheduler.sh
```

The script builds only the portable-policy targets. It supplies deterministic clocks and needs no Vulkan device, runtime loader, `Lossless.dll`, Gamescope, or Linux host. Vulkan, X11 and XCB headers are required by the Vulkan-facing policies and surface-adapter fixture; no live window-system connection is needed. Coverage includes:

- warm-up, ramping, multiplier ceilings, target behavior, and reset boundaries;
- Fractional placement, near-target native preference, Smooth Cadence, and cadence recovery;
- opt-in display-refresh targets, bounded 90/60/100 Hz transitions, missing-feedback fallback, manual-target restoration, and matching Steady/Fractional caps;
- Fixed refresh budgeting and direct ordered-FIFO acquire recovery;
- generated-frame request, admission, scheduling, and delivery accounting;
- acquire and present recovery policy, private-transition state, and swapchain retirement; and
- trace replay plus the scheduler matrix.

The matrix runs 384 combinations of source cadence, target, multiplier ceiling, and Smooth Cadence. Each simulation reports complete generated delivery and measures the final five seconds of a 25-second run, allowing every higher rung to qualify before measuring settled output. To keep its CSV output:

```bash
cmake -S . -B build/adaptive-policy \
  -DMAKO_BUILD_VK_LAYER=OFF \
  -DMAKO_BUILD_UI=OFF \
  -DMAKO_BUILD_CLI=OFF \
  -DBUILD_TESTING=ON
cmake --build build/adaptive-policy --target mako-adaptive-matrix
build/adaptive-policy/mako-render/mako-adaptive-matrix > adaptive-policy-matrix.csv
```

For a same-machine CPU-cost comparison, run `scripts/benchmark-adaptive-scheduler.sh`. Its nanoseconds-per-decision results are not portable performance limits.

The Linux package build runs the full registered CTest suite, which includes these policy tests. [Testing MAKO](../../TESTING.md) owns the complete portable checklist.

## Scheduling contract

`AdaptiveScheduler::planFrame()` is deterministic. It observes real-frame cadence, selects zero to four generated frames, and returns a `GeneratedFramePlan` whose interpolation timestamps are stored inline without per-frame heap allocation.

The presentation path keeps three facts separate:

1. **Requested:** timestamps chosen by Fixed or Adaptive policy.
2. **Admitted:** generated images the active transport can accept.
3. **Scheduled:** timestamps actually sent to the backend.

Full admission preserves requested timestamps. A batch admitted before backend work is evenly re-spaced across the real-frame interval when only part of it fits instead of taking an early prefix. The original real frame is outside the generated plan and keeps priority on failure.

Normal Adaptive ordered SDR preserves the 3.3 sequential FIFO acquire contract for fixed refresh. Requested or active VRR adds a presentation-policy adapter with bounded waits and zero-wait retries after pressure. [Transport recovery](#transport-recovery) owns the acquire deadlines, returned-image turnover proof, and retry rules. Allow Tearing does not select another policy because MAKO's private ordered SDR swapchain remains FIFO.

Admission pressure does not directly demote an already validated scheduler load. This also applies to zero-wait preflight in a headroom-tight pool, including Game Swapchain Images compatibility: an unavailable image skips the unavailable generated outputs for that batch and admission is retried on the next real frame, without a one-second stabilization or multiplier retry backoff. A headroom miss during an active multiplier evaluation can still reject that experiment, and qualified ordered-acquire recovery retains its separate load-failure contract. Sustained delivery loss can still reject an active multiplier through its normal delivery window, while partial headroom pre-admission during a multiplier evaluation can lower the capacity for that WSI context until game-owned recreation.

### VRR and fixed-refresh pacing paths

This map covers Frame Generation on MAKO Renderer's `OrderedSdr` transport, which also carries isolated HDR. FIFO describes the ordered pacing policy here: the private bridge can use lower MAILBOX with explicit future timestamps, as described in [WSI isolation](WSI-ISOLATION.md#guarded-gamescope-wsi-paths). References below to the separate nonblocking HDR transport mean legacy full-WSI `GamescopeHdr`, not isolated HDR. MAKO Renderer reads Gamescope VRR feedback to choose pacing behavior. The separate opt-in per-profile [Gamescope VRR control](CONFIGURATION.md#frame-generation) can temporarily change the compositor's live VRR value while a matched MAKO game runs; it never writes Steam's saved setting. VRR-aware behavior is selected when Gamescope explicitly reports active VRR, or reports VRR enabled without explicitly reporting an incapable connector. Missing VRR feedback selects the fixed-refresh column. An overlay can temporarily inhibit active scanout while the enabled setting keeps the VRR-aware path selected. The [WSI isolation guide](WSI-ISOLATION.md#vrr-and-tearing-feedback) owns feedback sampling and transport details.

These are MAKO plan and queueing rules; they do not prove physical scanout timing.

FIFO annotations alone do not guarantee that a generated batch is delivered intact when several images become ready together. Distinct future timestamps preserve each output; lower present-call counts remain submission evidence and must not be described as physical scanout. ### Desktop source-interval spacing

Without Gamescope, a desktop compositor gives MAKO neither refresh feedback nor an output clock. Ordered FIFO then shows each generated batch on consecutive refreshes and holds the real frame until the next source frame: at 5 FPS with Fixed 5x on a 120 Hz display, five outputs arrive within 42 ms, followed by a 158 ms hold. Fixed and Adaptive instead spread each complete batch across the measured real-frame interval when no Gamescope signal exists (process environment, detected root, refresh feedback, owned compositor timing or the scaling bridge), the lower transport is ordered FIFO without application presentation timing, Dynamic Cadence Recovery is not effective and no cap-interval preparation applies. Each output waits on the present thread for its share of the interval, the real frame last, matching the interpolation timestamps the plan already spaced. Base FPS Cap and GPU Headroom profiles are included unless their existing cap-interval preparation already spaces the batch, which Fixed and automatic Adaptive caps cannot do without a confirmed refresh. MAILBOX, IMMEDIATE and every Gamescope path are unchanged, and Adaptive still generates nothing below its 10 FPS policy floor.

Spacing engages after eight consecutive real-frame intervals of at most 250 ms lie within 10% of their median, which becomes the baseline; later windows may lower it to their median, for example after a slightly slow start-up cadence, but never raise it. A batch is spaced only when each output interval is at least 1/240 s and the real frame lands before the next expected source frame; history warm-up, partial admission, native frames and recovery keep ordinary delivery. Displayed timing remains quantized to the compositor's refresh, so 40 ms spacing alternates between 33 and 42 ms at 120 Hz.

The wait delays the real frame by up to `(n - 1) / n` of a source interval for `n` outputs: 160 ms for 5 FPS at 5x, 17 ms for 30 FPS at 2x. Video players and frame-limited games keep their cadence because the wait uses time they would spend idle. A throughput-bound game would lose frame rate instead, so the guard compares the upper median of the last eight intervals with the baseline. More than 1% plus 0.25 ms slower releases spacing, so a source that only just keeps up cannot lose a few percent unnoticed; when none of those intervals followed a spaced batch, the source changed on its own and requalifies without a penalty. Otherwise spacing retries after 5, 15, 30 and 60 seconds; after four consecutive failures it retries only once the unspaced cadence moves by at least 25%. Ten seconds of clean spacing forgets earlier failures. A median below 90% of the baseline means the source has sped up and requalifies without a penalty, as does a stall over 250 ms. Intervals up to that stall boundary remain in the median window so isolated hitches are tolerated but a sustained workload increase releases spacing, including when every interval exceeds twice the old baseline. A source that waits for its own next timer slot cannot show a faster cadence while spaced, so baselines up to 50 ms (at least 20 FPS) leave one frame unspaced every 10 seconds. Slower sources are not probed, preserving uninterrupted low-FPS video spacing. A timer-driven source below 20 FPS can therefore retain its old cadence after speeding up; effective Dynamic Cadence Recovery excludes this spacing policy and remains the option for such rate-changing applications. Diagnostics report `operation=source-interval-spacing` with `state=engaged` or `state=released` and the reason. Portable tests model video, frame-limited, throughput-bound, accelerating and timer-slot sources; they do not prove compositor scanout.

### Fixed mode

Fixed uses the configured 2x–5x multiplier. When Gamescope reports a nonzero refresh, a fractional display budget normally suppresses outputs that the display cannot consume; without refresh feedback, exact Fixed behavior is retained, and outside Gamescope [desktop source-interval spacing](#desktop-source-interval-spacing) spreads that batch across the source interval. The budget retains both early and late source-timestamp deviations, with at most one output of carried credit. Balanced timing jitter therefore cannot progressively suppress generated frames at an exact-fit cadence, while a slow period cannot build an unbounded reserve that defeats the display ceiling after the source accelerates.

With Smooth Cadence enabled and an ordered Gamescope SDR transport, Fixed requests its full configured multiplier and lets ordered FIFO backpressure pace real frames, including when Gamescope requests or activates VRR. This avoids a separate CPU sleep clock that can drift against physical VRR presentation. The policy requires confirmed refresh feedback, full private-output capacity, no explicit real-frame cap, and no active acquire recovery or Dynamic Cadence Recovery. The display budget continues to observe source cadence so a transition out of this policy restores the applicable budget without a cold start. First-frame and long-stall guards remain active. Without Smooth Cadence or when these guards fail, Fixed retains its normal fractional display budget.

Eligible [Zink swapchains](#zink-fifo-pacing) add a source cap at refresh divided by the Fixed multiplier, with Smooth Cadence either on or off. Dynamic Cadence Recovery disables this cap to keep native-rate measurement possible.

### Adaptive mode

Adaptive varies generated work toward `target_fps` without exceeding `adaptive_max_multiplier`. Fractional mode normally owns the long-term output budget and keeps timestamps evenly spaced within each real-frame interval; VRR consumes that target-clocked cadence without changing its multiplier rule. Near target, it may prefer native presentation when measured interval quality and output coverage are already sufficient.

#### Fractional real-frame priority

`adaptive_fractional_real_frame_priority = auto` is the default and adds no real-frame cap. With Base FPS Cap off or at least the target, qualified native presentation may exceed the Adaptive target up to the display ceiling, while the source pacer continues to enforce any manual cap. Only these eligible Fractional Automatic profiles additionally qualify sustained at/above-target cadence through the existing one-second hold; the output floor, quality checks and exit hysteresis remain authoritative. Steady, explicit priorities, below-target manual caps and Fixed recovery retain their previous scheduler qualification rules. Both Gamescope timing paths release the target ceiling and generated-work readiness lead only while that qualified native phase owns presentation. Occasional real-only Fractional turns, warm-up, native probes and recovery keep their existing generated timeline. Smooth Cadence on/off and multiplier ceilings share this policy. A faster source hidden by generated backpressure still needs Dynamic Cadence Recovery to become observable.

Explicit Low, Medium, High, and Very High priorities apply target-relative real-frame caps using 3:2, 2:1, 3:1, and 4:1 real/generated ratios. At a 120 FPS target those caps are 72, 80, 90, and 96 real FPS. The explicit cap takes precedence over the manual cap only while Fractional Adaptive is active; Fixed and Steady ignore it. Below-target manual caps, explicit priorities and Steady retain their output pacing. A priority or target change resets the real-frame pacer and affected scheduler policy through the ordinary live profile transition.

#### Output timing within an existing base cap

On direct ordered transport, including admitted spatial scaling and variable surfaces, capped Fractional can prepare and space outputs during the existing source-cap wait. It keeps one target-output clock across changing batch sizes and returns to the game no earlier than the original cap deadline. Scheduler cadence uses that reserved deadline; resource timeouts retain wall time. Interpolation timestamps and generated counts stay scheduler-owned. Output slots must fit between completed CPU preparation and the source deadline, otherwise ordinary delivery applies. Late arrivals, loading stalls, native preference/probes, partial admission, live policy changes, and unsupported batches discard output timing state instead of accumulating catch-up debt. This is bounded use of cap slack, not a guarantee of even delivery below the cap or with an uncapped source. Preparation stays after the source-cap wait while generated-image admission is under pressure or the returned image pool cannot fit the active policy’s maximum generated batch, preserving zero-wait retry and higher-rung qualification opportunities. Target-matched automatic pacing on direct FIFO, active acquire recovery and application-owned timing retain their current path. Renderer-owned Google or EXT timing uses its compositor output clock instead of CPU output deadlines. Validate source intervals and independent compositor completion separately.

The isolated Gamescope bridge and Renderer-owned Vulkan timing can prepare inside the same source-cap interval, including target-matched automatic Adaptive caps, scaled and HDR output. Each keeps its own ordered output clock instead of adding CPU output deadlines. The existing source deadline limits submission backpressure for that batch; display targets, queue readiness, generated counts and real-frame presentation waits remain unchanged. Control returns to the application no earlier than the reserved cap deadline. This prevents cap sleeping followed by output spacing from consuming part of the next source interval. The same timing-owner, image-capacity and admission-pressure guards apply, and every application present clears the previous batch’s submission budget.

Without a compositor output clock, Adaptive automatic caps can use this interval only when the target is strictly below the confirmed refresh rate, with Smooth Cadence either on or off. The scheduler still chooses every generated count and interpolation timestamp. Preparation does not choose an Adaptive rung or replace cap refinement, FIFO handoff or recovery. Unknown refresh cannot qualify automatic early preparation.

Exact Fixed uses the same bounded output owner when an explicit Base FPS Cap and the complete configured 2x–5x batch fit within a confirmed refresh rate, with Dynamic Cadence Recovery disabled. Its output rate is the cap multiplied by the configured multiplier; the saved Adaptive target has no effect. For example, a 30 FPS cap with Fixed 2x on a 120 Hz display schedules outputs about 16.67 ms apart instead of submitting a pair together every 33.33 ms. Partial batches, history warm-up, disabled generation, slow preparation and late source frames retain ordinary delivery. The existing source-return deadline is preserved; no additional cap, worker, queue, or setting is introduced.

When demand temporarily exceeds the validated multiplier ceiling, the target clock retains less than one output of bounded credit instead of wrapping it away. This lets a source returning from an external throttle recover an achievable integer cadence without dropping generated work on ordinary timing jitter, while still preventing impossible whole-output debt from accumulating or producing later catch-up bursts.

#### Integer pacing handoffs

Smooth Cadence may retain a delivery-validated integer multiplier. Fractional Adaptive normally retains its moving target clock, but an accepted constant cadence already replaces that clock with a fixed generated-frame count. Under requested or active VRR with ordered Gamescope SDR and matching refresh, this accepted Fractional 2x–5x cadence may hand pacing to FIFO when it has no manual or Fractional Real Frame Priority cap and Dynamic Cadence Recovery is off. Its projected full rate must be within 98–102% of target for 2x or 98–125% for 3x–5x. Variable Fractional plans keep their target clock and do not request extra generated work.

On ordered Gamescope SDR with matching refresh, Steady Adaptive hands a proven 2x cadence to FIFO. Under requested or active VRR, a validated 3x–5x Steady rung can also request its complete integer batch and hand pacing to FIFO when its projected full rate is at least 98% and at most 125% of the target; the upper bound limits the predicted real-FPS reduction from FIFO backpressure to 20%. This higher Steady experiment does not require a separately accepted constant-cadence probe, so it can cover a validated variable 3x workload such as a 50 FPS source at a 120 FPS target. Probe, recovery, and transport guards restore normal pacing. A planned lower-load efficiency probe pauses a higher Steady VRR FIFO handoff without starting its 60-second retry, so rejection can restore that rung and acceptance does not delay a later revalidated return. A genuine lost qualification or safety guard still starts the retry only for that rung. Confirmed fixed-refresh eligibility keeps the established target/multiplier base-cap ladder for validated Steady 3x–5x demand and does not use either higher-rung FIFO policy. Fixed requests its full multiplier under eligible ordered FIFO regardless of VRR feedback. Explicit Fixed caps, Dynamic Cadence Recovery, transport recovery, and insufficient private-output capacity keep Fixed's normal budget policy.

Every Steady or accepted Fractional FIFO handoff also ends when the game sustains its own faster clock, such as a 62.5 Hz engine tick at 2x and 120 Hz, or a 50 FPS limiter at 3x and 120 Hz. A source paced by presentation settles at confirmed refresh divided by outputs per real frame: a higher VRR rung may enter up to 25% above that rate, but FIFO backpressure slows it within the bounded queue. After a late frame, it refills that queue only once. A faster independent clock instead supplies surplus frames in successive windows and paces real frames unevenly.

`FifoSourceOverrunWatch` ignores the first 250 ms after a handoff, refresh or rung change, or source gap longer than 250 ms. It then compares real frames in consecutive windows of at least one second with the refresh-limited rate. Three consecutive windows with at least 1.5 surplus frames each restore the rung's pre-handoff pacing, such as Steady's half-target cap, with `adaptive-smooth-cadence-pacer-restored reason=fifo-source-overrun`. Counting surplus frames keeps the same margin at every refresh and multiplier. The affected rung stays out of FIFO until a profile change, pacing-owner feedback change or swapchain recreation resets handoff state; other rungs keep their eligibility. Steam-menu focus discards partial evidence.

Gamescope rounds the panel's millihertz refresh to the nearest hertz, so its report can be up to 0.5 Hz below the physical rate. A paced source would appear to overrun only if the report were about 3 Hz low at 2x, or more at higher rungs. A false restore retains the rung's validated pre-handoff pacing; a high report makes the check more lenient. Policy tests preserve a 2 Hz margin at 2x and 3 Hz at 3x–5x.

VRR feedback does not itself choose an Adaptive multiplier, target, ceiling, or recovery. It may select a full-batch FIFO presentation policy for an already validated higher Steady rung; the scheduler rechecks that rung after its frame stages before requesting the full batch. It may also hand an already accepted constant Fractional plan to FIFO without changing that plan's generated count. A live feedback transition resets the pacing helpers whose ownership changed; it preserves the source estimate, temporal history and validated Adaptive level, and it cannot arm recovery or recreation. A confirmed VRR-enabled preference change can additionally refresh a failed higher-rung retry after a five-second settling period and fresh lower-load qualification, as described under menu return below. Active-scanout changes alone retain the existing retry history. Applied integer pacing separately verifies its measured workload cost, as described below. Allow Tearing is recorded but has no scheduling effect because the ordered SDR path deliberately owns FIFO.

##### Zink FIFO pacing

The following policies apply only to swapchains with a [Zink application acquire window](LIFECYCLE.md#zink-application-acquire-window). Zink's game thread waits for its presentation worker before acquiring another image. When FIFO stays full, that extra handoff can miss refreshes even at the correct average rate: at 2x and 120 Hz, real-frame intervals can alternate around 25 ms and 8 ms. The source-overrun count cannot detect this because no surplus frames arrive.

**Fixed source cap.** With Frame Generation active, a known nonzero Gamescope refresh, no explicit Base FPS Cap and Dynamic Cadence Recovery off, MAKO paces the Zink source at refresh divided by the configured multiplier: 60 real FPS at 2x and 120 Hz, for example. This is the rate a full FIFO batch can sustain. Smooth Cadence may be on or off. An explicit cap remains authoritative; GPU Headroom can lower the effective cap. Dynamic Cadence Recovery omits this automatic cap so native-rate probes remain possible, and Adaptive retains its own caps and handoffs. Disabled or refresh-paused generation and missing refresh feedback add no Zink cap. Changes log `zink-refresh-limited-cap` when presentation diagnostics are enabled.

**FIFO backlog detection.** MAKO measures its own generated-image acquire waits on these swapchains. A frame counts as waiting when that duration exceeds a quarter refresh. During an Adaptive FIFO handoff, the watcher allows 250 ms to settle, then three consecutive one-second windows with at least half their frames waiting restore the rung's pre-handoff pacing. The diagnostic is `adaptive-smooth-cadence-pacer-restored reason=fifo-presentation-backlog`; the rung remains out of FIFO until the same resets as a source overrun.

**Capped backlog drain.** A compositor stall can leave FIFO full behind a source cap that matches the display's consumption rate. For capped Fixed or Adaptive Zink, a half-second window with at least half its frames waiting delays the next real frame by one refresh to retire one queued output. A window whose measured source rate is below 85% of the cap cannot trigger a hold: a slower consumer, such as Gamescope's frame limiter, must not be treated as a drainable backlog.

A window with at most a tenth of its frames waiting ends the episode. Each episode permits `round(refresh / cap) + 2` holds, clamped to 4–8; reaching that limit without clearing the waits suspends holds for 30 seconds. Diagnostics record `fifo-backlog-drain action=hold` or `action=suspend`. A source gap over 250 ms, cap or refresh change, Steam-menu focus or swapchain recreation discards partial evidence. Other engines do not consume these acquire waits.

#### Measuring applied integer pacing

For target-matched ordered Smooth Cadence with automatic integer pacing available, an accepted 3x–5x workload projecting at least 95% of target retains its adjacent lower-load baseline for at most eight seconds. If that same rung enters VRR FIFO or the fixed-refresh automatic target/multiplier cap during this window, MAKO discards the first interval, permits 250 ms of turnover, then measures at least one second of actual source intervals and completely delivered output counts. A later applied handoff starts its own bounded measurement without reusing the expired promotion baseline: after measuring the paced workload, it temporarily selects the adjacent lower workload through the existing efficiency-probe owner, releases FIFO or applies the lower automatic cap, permits 250 ms of turnover, and obtains another continuous one-second delivered sample. Each sampling phase is bounded by eight seconds from its actual activation. Planned probe release and return remain one pacing lifetime until the same validated rung resumes, including when FIFO entry or automatic-cap qualification takes longer than the 250 ms sample-settling interval. A workload/rung or pacing-owner change, timing reset, transport backoff, impossible fast burst or rescue invalidates that retained identity. Once the planned return completes, a later unrelated release must qualify a fresh comparison.

The lowest adjacent workload that measurably reaches at least 98% of target is preferred over a lower workload that misses that floor, provided its output gain clears the existing 2%-of-target margin. Intentional FIFO or automatic target/multiplier pacing can therefore trade real-frame rate for the requested output: at a 120 FPS target, 54 real FPS at 2x supplies 108 output FPS, and settled 40 real FPS at 3x supplies 120 and is retained. If the lower workload already reaches the target, the higher workload cannot claim this preference. If the higher workload also misses the target, its output gain must still pay for the full real-FPS loss plus the margin; a 54-to-36 real-FPS change at 3x produces no gain over 108 and is rejected. The same comparison covers 3x–5x with no per-game or transport-specific thresholds. Delayed 16- and 27-second handoffs still require a fresh lower sample, so an old deficit cannot authorize extra work when the current lower workload already reaches the target. Accepted applied pacing reports `reason=settled-output-qualified`.

This follow-up check prevents another promotion or an independent lower-load efficiency probe until it resolves. Before integer pacing takes effect, a projected rate below 95% of target cancels the recent watch so useful 4x/5x qualification is not delayed by an unavailable pacing experiment. Constant-cadence qualification continues before the handoff so an uncapped Fractional plan can qualify; an active fresh comparison pauses it across both samples to preserve the planned pacing release. Quarter-second source windows in each measurement must remain within the existing 15% cadence envelope. Missing or partial generated delivery, an unexpected pacing-owner or rung change after sampling starts, timing/history reset, native rescue, impossible fast bursts, acquire backoff, changing source cadence, or expiration cancels incomplete evidence without rejecting the accepted workload. Interrupted fresh probes restore the retained workload through their existing owner. A measured rejection resets only transient constant-cadence state and the output clock, returns to the adjacent lower rung, and uses the ordinary 5/15/30/60-second retry ladder plus fresh lower-load qualification. Planned FIFO probe pauses and measured exits do not also start a separate 60-second handoff-failure cooldown, including uncapped Fractional comparisons. An expired baseline never acquires authority over a later scene. Manual and explicit Fractional priority caps, exact Fixed, 2x admission, unmatched targets, HDR transport, and Dynamic Cadence Recovery retain their existing policies. Requested timestamps and accepted output counts do not prove physical VRR scanout or input latency.

#### Adjacent-workload promotion

Every ordinary Adaptive promotion from 2x through 5x compares adjacent workloads. A current level that supplies at least 98% of the target does not probe a higher multiplier; a recovered source cancels a pending target deficit before promotion. Below that boundary, the ordinary one-second target-deficit guard remains in place and overlaps the lower-load qualification window. In both Steady and Fractional, a 3x–5x trial additionally requires two continuous seconds of fully delivered lower-load cadence within the existing 15% qualification envelope, measured in 250 ms windows of the canonical source estimate; recovering to the target cancels that candidate. Its highest sampled window rate supplies the adjacent-workload comparison baseline, so a brief low point cannot make extra GPU work look cheap. Initial native-to-2x admission retains its existing delay.

The higher load is accepted only when generated delivery is healthy and either its target-capped displayed-FPS gain pays for the real-FPS cost measured during the same bounded probe, or a 3x–5x trial closes a proven target deficit. Ordinary cost decisions retain their one-second trial. When only target preference can justify acceptance, the existing trial may extend by 250 ms for output-clock turnover before requiring at least one second of actual source intervals and accepted output averaging at least 98% of target, one delivery observation per interval, and complete generated delivery throughout the trial; a final smoothed-FPS estimate alone is insufficient. Missing observations, partial delivery, or bypassed intervals invalidate that preference without weakening the ordinary cost rule. Initial native-to-2x admission keeps its existing cost rule. Promotion to 3x–5x must additionally clear an output gain of at least 2% of the configured target; below-target trials must pay the real-FPS cost as well. This small margin rejects near break-even trades such as a 40-to-30 real-FPS drop for an 80-to-90 displayed-FPS gain at a 120 FPS target, while preserving the existing 2x admission rule. There are no multiplier-specific retention percentages, base-collapse boundaries, bridge probes, or 2x-only hitch exception.

A rejected level preserves its proven lower-load baseline through the bounded retry delay. After that delay, higher-level retries require either recovery to that baseline or two continuous seconds of fresh lower-load evidence within the existing 15% cadence qualification envelope. Every generated frame in the fresh sample must report complete delivery; missing observations, delivery pressure, timing resets, or a moving source restart qualification. Intentional Dynamic Cadence Recovery native samples pause the qualification clock and do not count toward its two seconds, so short probe intervals cannot indefinitely restart otherwise valid evidence. A fresh sample replaces the obsolete baseline with its highest observed window rate while preserving the failure count and increasing retry delays. The next actual trial still has to pass the same adjacent-workload and delivery checks; time alone cannot authorize promotion. After a rejected first 2x probe, native presentation may instead adopt a new gameplay baseline when the bounded cooldown has elapsed and output remains continuously below the near-target envelope for two seconds; retry delays back off from 15 to 30 and 60 seconds after repeated rejection. This prevents an ordinary scene change from leaving Adaptive permanently native-only without weakening the same-probe workload comparison. Later gameplay cadence cannot retroactively classify an accepted workload as a transport failure or authorize recreation; Adaptive's established cadence-rebasing policy remains feature-owned.

Lower-load Smooth Cadence efficiency probes retain their separate user-selected pacing behavior.

#### Automatic integer base caps

The fixed-refresh Adaptive 3x–5x base-cap policy requires one second at or above 95% of its selected cadence before entry. An active constant plan bounds the selected multiplier even when a higher workload remains validated: accepted 2x keeps the normal half-target cap, and a newly selected lower multiplier immediately releases any stricter old cap before qualifying its own. Without a constant plan, the validated workload still owns higher-rung qualification. An active cap tolerates dips down to 90%; a lower cadence or a return to the previous multiplier's range must persist for 250 ms before releasing it. This prevents entry-threshold jitter from repeatedly resetting the real-frame pacer. Transport guards, scheduler recovery, ramp evaluation, loss of eligibility and a return to 2x still restore normal pacing immediately; lower-load efficiency probes retain their separate cap transitions. The Steady 2x FIFO handoff requires a close target match to enter. An accepted fixed-refresh handoff retains the same rung while the scheduler retains its qualified constant cadence. The scheduler already requires 500 ms continuously outside its useful retention range before releasing that cadence; a single estimate outside the stricter FIFO entry window must not start a 60-second handoff retry. Transport, recovery, scheduler-probe, refresh-match and profile guards still exit immediately. Requested or active VRR retains its existing handoff policy, with the scheduler continuing to own sustained cadence and delivery exits. Higher VRR rungs use the 125% entry bound and a per-rung retry delay. Fixed's ordinary FIFO path has no automatic base-cap qualification or timed CPU sleep; [Zink's refresh-derived source cap](#zink-fifo-pacing) is a separate exception.

A fresh adjacent lower-load probe can release queued application returns when it lowers the automatic cap or releases FIFO. Impossible fast intervals inside its existing 250 ms settling period remain real-only and are excluded, together with their following return interval, from measured workload evidence. They do not cancel and recursively restart the probe. The settling deadline is never extended; bursts after it expires, incomplete measured delivery, owner changes and transport recovery still invalidate the comparison.

#### Smooth Cadence rescue

`adaptive_auto_base_fps_cap` normally starts at half the target. Smooth Cadence rescue may release only this automatic cap during a one-second real-only pacing measurement; manual, explicit Fractional priority, and Fixed caps remain authoritative. A qualified Ordered-SDR cadence that exits its useful range retains its accepted baseline for at most two seconds: at least one second of actual source intervals must then show both a 22% source collapse and projected output at or below 80% of target before one rescue attempt starts. This catches gradual or bursty deterioration whose deepest sample comes after the cadence exit, without probing every low-FPS scene. The existing 15-second cooldown and requirement for a newly qualified stable cadence prevent repeated attempts in an unchanged heavy scene.

The rescue measures frame count divided by accumulated source interval time, discarding the first interval after a policy change. At the end of its one-second history-only measurement, it always restores the configured automatic cap and the previous generated workload, regardless of native headroom. A second one-second sample verifies recovery under that restored policy: at least eight source samples must recover 90% of the accepted baseline and improve 25% over the collapsed rate, with actual generated delivery and no missing or partial delivery observations. Planned output counts and generated delivery observations use bounded counters in the existing scheduler; no new polling, allocation or GPU query is needed. Native headroom is diagnostic information and cannot authorize a retained cap override. Ordinary higher-load trials wait until verification ends, then resume their existing qualification rules even when recovery failed.

Success, failure and interruption all leave the configured cap in force. Timing resets, hard cadence disruptions, impossible fast bursts, stabilization and generated-acquire backoff cancel an incomplete attempt; verification cancellation records its reason and cannot later commit stale evidence. A natural scene improvement can still coincide with the probe, but no outcome preserves a cap override beyond the native measurement. Expiration is consumed by the next scheduling call; a game that stops presenting receives no background recovery work. The existing cooldown and fresh stable-cadence qualification bound retries. The guard never changes saved settings, Steam hooks, Vulkan resources, swapchain lifetime or exact Fixed behavior. Diagnostics report `adaptive-rescue-start`, `adaptive-auto-base-cap-restored` with `reason=rescue-measurement-complete` before `adaptive-rescue-complete decision=verify-restored-policy`, then `restored-policy-recovered`, `restored-policy-not-recovered`, or an interruption reason. These observations report recovery under the configured policy, not the cause of the preceding slowdown.

Portable tests cover full-target capped recovery with and without native headroom at 90 and 120 FPS, persistent heavy scenes, natural scene recovery, a modeled feedback loop cleared by a brief reset, and a modeled slowdown that would need continuous uncapping. Five-minute continuations apply the production cap owner and require the configured cap outside the native measurement in every scenario. Additional regressions cover repeated collapses, missing and partial generated delivery, brief headroom, ordinary short dips at 60/90/120 FPS, and interruptions in both measurement and verification. Manual and explicit Fractional caps, Fixed isolation and live policy transitions retain their existing contract tests. These simulations do not establish a real-game false-positive rate or prove resolution of a Steam Deck long-session stall.

#### Lower-load probe retries

An ordinary lower-load Smooth Cadence probe keeps the proven higher rung while testing the cheaper workload. Its initial 250 ms check, with one optional 250 ms settling extension, can reject an insufficient workload but cannot alone accept it. A promising result must then sustain at least one second of raw source intervals with one complete generated-delivery observation per interval, and both its measured average and final cadence estimate must reach 98% of target. Missing, partial or duplicate delivery, native bypass, acquire backoff, or a timing reset prevents incomplete evidence from accepting the downshift. This avoids retaining a briefly fast 2x workload that settles below target after queued work drains; sustained target-capable 2x remains eligible. The counters belong to the existing scheduler and add no GPU work, allocations or polling. Separate applied-integer-pacing comparisons retain their own continuous measurement owner.

Rejected lower-load Smooth Cadence probes retain their 60-, 120-, or 300-second retry deadlines independently for each tested multiplier. Cadence loss, stalls, menu returns, and transport history refreshes preserve completed rejections without extending their deadlines; timing resets discard only an incomplete probe's evaluation. Requalifying the same cadence therefore cannot repeatedly restart an unsuccessful downshift. A different multiplier remains eligible for its own experiment, and independently observed source improvement can still qualify a useful lower cadence. Confirmed Dynamic Cadence Recovery, qualified near-target native preference, or a newly constructed scheduler clears obsolete rejection history. This applies to Steady and Fractional Adaptive probes from 3×→2×, 4×→3×, and 5×→4×; Fixed and 2×→native planning do not use this efficiency-probe policy.

#### Bursty source cadence

A transient source-rate burst above the larger of three times baseline or twice target is treated as native activity and does not advance policy clocks.

Cadence-drop detection holds the proven interval while confirming three consecutive samples at least twice as long. It also accumulates those candidate samples in a shadow smoothed estimate: if the next sample rejects the sustained-drop hypothesis, the estimator incorporates the delayed observations before the current interval. Discarding them instead can lock onto only the fast half of a bursty stream, for example reporting 125 FPS for alternating 8/32 ms intervals whose actual rate is 50 FPS, and suppress useful generated work. Timing resets, impossible fast bursts, and transport backoff discard pending drop evidence. The existing hard-stall, history, delivery, and multiplier bounds still apply. Portable tests cover both recovery policies and Smooth Cadence settings; Gym's `adaptive-bursty-source` row exercises a 75 → noisy 50 → 75 FPS round trip with a 150 FPS target and 240 Hz headless Gamescope. This is source-cadence evidence relevant to mouse-stutter investigation, not a simulation of HID polling, game input, or physical scanout.

### Dynamic Cadence Recovery

Dynamic Cadence Recovery is an optional per-profile policy for games or emulators that switch native rates. Ordered FIFO can make a native 60 FPS mode look like 30 FPS when generation is active, so MAKO periodically requests a native-only sample. When MAKO owns an output timeline, the presentation owner supplies its already-scheduled deadline. A native probe captures that horizon once, discards intervals before it and the interval crossing it, then starts its cadence measurement. New native-only outputs cannot extend that captured horizon. An ignored fast-burst interval can finish this drain when it reaches the horizon, but cannot count as a recovery confirmation; the next complete post-drain interval is measured normally. This uses existing CPU timing metadata and adds no GPU wait, query, guessed drain duration or transport polling; unbridged probes retain their immediate measurement. Three consecutive samples at least 25% faster than the captured baseline confirm the new cadence. A rejected probe resumes the ordinary plan for its frame and adds no generated frame to it: a source already running near its target plans none, and an added frame would fill the FIFO slot that holds it back to half rate. If that sample reaches the native-preference envelope, the probe keeps generation paused through the existing one-second quality qualification, including a first sample at or above target followed by cadence slightly below it. After confirmation, that opt-in native measurement counts all source intervals in bounded quarter-second windows, including queued bursts, and uses their frame-count/time rate for native-preference qualification and retention. A single late turnover frame must not immediately cancel the measurement or bias it toward only the slower half of a bursty native stream. The existing 95% output floor, interval-quality comparison and one-second qualification remain authoritative; a below-floor measured window cancels qualification. Timing resets discard the measurement, and an intervening generated-image recovery probe also restarts native confirmation and its normal retry interval, so samples on opposite sides cannot masquerade as consecutive native frames. Ordinary source estimation, promotion evidence, recovery-disabled behavior and Fixed retain their existing policies. Sparse generated FIFO work must not contaminate that native measurement and hide the recovered rate again. A loss of qualifying cadence cancels the measurement and restores ordinary planning; Fixed recovery does not use native-preference qualification; Adaptive keeps its existing stable-cadence and recovery guards.

Adaptive keeps its configured target and ceiling. Fixed uses confirmed Gamescope refresh as its target and treats its multiplier as a ceiling; without refresh feedback it stays exact Fixed. Enabling recovery disables manual and automatic base caps. The probe does not run on the nonblocking HDR transport.

Each rejected probe costs native-only frames: one when unbridged, plus the captured drain on an owned output timeline. To avoid paying that cost where a probe cannot succeed, the layer times the application's own image-acquire and present calls on each thread and reports the share of the previous source interval spent inside them. This adds four steady-clock reads per frame and no GPU work, query or wait. A source held by generated FIFO work waits inside MAKO for most of each interval, while a self-capped source barely enters it: MAKO Gym measured about 2% in capped 30 FPS phases and about 100% while Fixed Smooth Cadence held a 60 FPS-capable source at 30. A source able to rise by the required 25% must spend at least a fifth of each interval waiting. When every interval since the last probe decision stays below a tenth, the timer probe is skipped, at most three times in a row, so a self-capped scene is still probed at least every fourth interval. Three consecutive capped frames arm a held trigger: the first three consecutive frames at or above a fifth then probe at once, before the timer, because a capped source that starts waiting on MAKO may have switched to a faster native mode. Only a fresh capped period re-arms the trigger, so a held source that cannot rise keeps the configured timer. The trigger also disarms once the observed source rate rises more than 10% above its capped rate: ordinary planning already sees that rise, and a probe measured against the risen baseline would reject and restore the generated work holding the source, as Gym's 60 → 119 FPS round trip showed before this guard. The capped rate is the lowest during the capped period, and a trigger disarmed during that period re-arms only after it ends, because a rise can begin with a few fast frames before FIFO work makes the source wait inside MAKO. Unknown evidence, such as acquire and present on different threads, a different swapchain, multi-swapchain presents, or any unmeasured frame in the window, keeps the configured timer exactly. Lower-layer limiters that sleep inside the present call count as time inside MAKO and therefore only retain today's timer. Application present waits (`vkWaitForPresentKHR`) are not counted, so a source paced by them can look capped while held; the safety probe bounds that delay to four intervals, and Proton translation layers need hardware qualification before this evidence is trusted. The `dynamic-cadence-probe-start`, `dynamic-cadence-probe-skipped`, `dynamic-cadence-probe-rejected` and `dynamic-cadence-recovered` records report `native_frames` and `native_ms` (plans the probe emitted without generated frames, and source time from probe start to decision; a rejecting frame already resumes generation and is not counted), `reason` (`interval`, `held`, `skip-limit` or `capped`) and `layer_share_max`, the largest share before the decision or `unknown`. The `adaptive` and `performance` diagnostics presets retain these records.

## Transport recovery

Fixed ordered generated-image acquisition uses one application-present deadline, not a refresh-derived slow-call threshold per generated image. Each image receives only the remaining cumulative configured budget. An unconfigured Fixed path with relief headroom retains its unbounded compatibility contract. When the image pool fits the Fixed batch but lacks an additional relief image, the shared deadline is at most 50 ms; a shorter configured deadline wins. Headroom-tight admission remains nonblocking. Normal Adaptive ordered delivery preserves the established sequential FIFO acquisition point. Fixed refresh retains the configured sequential acquire contract from 3.3. Requested or active VRR uses the same finite 50 ms application-present ceiling because its release timing is variable. The VRR deadline cannot recursively enlarge when its own wait lowers measured source FPS, and any shorter explicit ceiling remains authoritative. The presentation adapter does not feed its acquire delay back into the source interval. Returned image count and batch size determine the turnover proof, independently of refresh rate, source FPS, device identity, or a timer.

A `VK_TIMEOUT`/`VK_NOT_READY` result, exhaustion of the configured cumulative acquire budget, or completion of an ordered batch after that cumulative wall-clock budget has been reached starts blocking ordered transport recovery. The deadline is the explicit application-present budget; it is not derived from output FPS, GPU load, device, resolution, scaling, or post-processing cost. Fixed-refresh Adaptive and direct Fixed deadline failures enter the ordered native-drain retry ladder of 250 ms, 500 ms, one, two, five, 15, and 30 seconds. Recovery probes retry one image using the explicit configured acquire budget or one confirmed display period, and without either contract the retry is nonblocking. An Adaptive VRR timeout instead drains already scheduled backend timeline values, presents the real frame, and arms zero-wait admission before later backend work. Availability resumes generated delivery immediately, while consecutive complete batches must cover one returned-image turnover before another bounded wait is permitted; persistent misses remain visible to the ordinary delivery window without turning one VRR hold into a 5-30 second multiplier shutdown. There is no FPS-derived acquire deadline, native-cadence hold, repeated-episode counter, failure-count-derived acquire timeout, or timed recovery window.

A confirmed Steam-menu return or an explicit live generation-policy transition arms one one-shot recreation permission. Multiple policy writes under confirmed Steam UI focus are last-value-wins: generation remains suspended, the scheduler is reconstructed once from the final values on return, and that return owns the single transport permission. The first generated-image acquire batch completed within its configured budget consumes the permission without action. If an acquire timeout, budget exhaustion, or cumulative deadline overrun occurs first, one successful retirement-protected real present may request a game-owned recreation; the context cannot signal it twice, and a replacement context initializes from the current Gamescope return sequence so the same old event cannot rearm a loop. Fixed direct deadline failures retain bounded in-place backoff. Adaptive VRR gameplay instead uses bounded delivery followed by nonblocking pressure retry; ordinary VRR pressure cannot authorize recreation or directly start a long multiplier backoff.

A recovery probe runs only when temporal history is ready and the current Fixed or Adaptive policy requests generated work. A real-only policy frame performs no generated-image acquisition and leaves the pending probe intact for the next eligible frame; it cannot count as a probe failure or increase recovery backoff.

Lower `QueuePresentKHR` duration is diagnostic only. A successful but slow present cannot quarantine generation, change a multiplier, warm history, or request recreation. MAKO cannot reliably distinguish compositor throttling, stacked GPU work, VRR behavior, or a game-scene change from a wedged queue by elapsed time alone.

Cadence stalls and low FPS never request swapchain recreation. Confirmed Gamescope Steam UI focus suspends generated acquisition and scheduler observations while preserving real/scaled presentation. Menu entry discards incomplete ordered-acquire retry state; a confirmed return restarts exactly three history frames and arms the one-shot direct-failure permission across exact Fixed, Fixed + Dynamic Cadence Recovery, Fractional Adaptive, and Smooth/Steady Adaptive. There is no additional time-based menu-return settling delay when a proven Adaptive level exists. Live Fixed/Adaptive mode, multiplier, base-cap, target, Smooth Cadence, and Dynamic Cadence Recovery changes apply the same transient boundary. A confirmed return retains a proven Adaptive level and its best lower-load baseline. Only a retained workload whose source rate and multiplier projected at least 98% of the target arms the post-return target hold. It remains the workload ceiling during the existing five-second higher-probe delay, and then until either the target recovers or the same continuous, delivered lower-load qualification establishes a changed scene. A brief menu return cannot immediately increase generated work, while a game that settles at a genuinely lower rate can resume ordinary adjacent-workload trials without first revisiting an obsolete FPS value. A retained workload that never reached target does not invent that target proof. Unknown feedback may end menu-only suspension with fresh history but cannot authorize a rebuild. Fixed never launches a cadence-collapse probe: its user-selected multiplier remains exact unless a direct Vulkan failure owns bounded transport safety.

Menu returns preserve failure counts and remaining cooldowns for rejected native-to-2x and higher-multiplier trials. After cooldown, fresh source and lower-load evidence are still required; menu time cannot qualify a retry. Explicit policy resets discard this history. A confirmed change to the Gamescope VRR enabled preference on an ordered Adaptive path can discard stale higher-load failure history and schedule a fresh trial after the ordinary five-second settling delay plus continuous delivered lower-load qualification. It preserves the accepted rung, source estimate and temporal history, including when the preference changes under Steam UI focus. Initial or missing feedback, active-only overlay changes, Allow Tearing, an incapable connector, active transport recovery, an ongoing trial, and rejected native-to-2x work do not refresh that retry. The existing `adaptive-recovery-resume-scheduled` record identifies this with `reason=gamescope-vrr-policy-change`; the event does not start recovery.

After a confirmed menu return or Fractional/Steady recovery event, history warm-up and scheduler planning use the same source-cadence boundary: the application-present start after real-frame pacing, or the reserved cap deadline when a capped plan prepares during that wait. Backend scheduling and GPU waits must not move that event-recovery clock forward within the frame: doing so seeds cadence from only the remaining fraction of a frame and can repeatedly mistake a steady source for a cadence drop. Ordinary generated-image timeout recovery deliberately retains the 3.3 completion boundary, preventing recovery work from being reinterpreted as new gameplay cadence. This applies to Adaptive and Fixed + Dynamic Cadence Recovery; exact Fixed has no scheduler cadence history. Portable recovery coverage models 12 ms of private work inside steady 60 FPS event-recovery frames; hardware recovery and external-overlay suites must still prove resumed delivery.

`GeneratedDeliveryWindow` compares requested outputs with outputs queued inside MAKO's budget. It does not claim compositor scanout. Diagnostics distinguish requested, admitted, scheduled, and delivered counts.

Private Flow Scale, model, or generated-capacity changes retain the old policy while replacement resources are prepared. Capacity growth that does not fit the current WSI pool remains pending for game-owned recreation. [Runtime configuration transitions](RUNTIME-TRANSITIONS.md) owns that lifecycle. Ultra Performance is a restart-bound resource policy, not a separate scheduler.

## GPU Headroom

The controller averages ten background samples over approximately two seconds, waits for stable source cadence, and adjusts the existing real-frame cap at most every two seconds. Persistent overshoot lowers the cap by at most 5% per decision; spare capacity restores it by 2%, or 20% when utilization falls far below the target. When another cap, such as Adaptive's automatic integer cap, holds the source more than 5% below the Headroom cap, spare capacity is judged from utilization projected to the Headroom cap's rate (measured utilization × Headroom cap ÷ source rate). Utilization at the lower rate says nothing about the cap's rate, and raising a cap that limits nothing until it releases would return the full load at once: at a 120 FPS target, 80% at 40×3 under a 49 FPS cap projects to 98%, so the cap holds instead of releasing 60×2 back to 100%. A deadband avoids reacting to every utilization spike. An eight-second source-rate history preserves the recent healthy rate while smoothed telemetry catches up with a heavy scene, then expires old peaks. Switching Off, a source pause longer than 250 ms, or losing fresh readings releases only this additional cap. Existing manual and Adaptive caps still apply.

GPU Headroom adds a slowly adjusted source cap to the existing `RealFramePacer`; it does not bypass Adaptive promotion, generation-cost validation or the available generated-image ceiling. Fractional and Steady can generate more frames when their existing policy qualifies them. The real-frame floor is the larger of 20 FPS and Target FPS divided by the smaller configured or admitted maximum multiplier. Reduced transport capacity raises this floor on the next frame, without waiting for the next utilization decision. Target delivery remains conditional on GPU cost and that capacity. Fixed retains its selected multiplier and may reduce output FPS.

While the additional cap is active, Smooth Cadence's separate source-cap ladder and FIFO source-pacer handoff yield to it. Output timing retains its existing owner, and small cap changes preserve the source-pacer phase instead of releasing an early frame. Off and unavailable telemetry restore ordinary policy; confirmed Steam-menu suspension and ordered-acquire recovery take precedence. Dynamic Cadence Recovery remains mutually exclusive. See [GPU Headroom configuration](CONFIGURATION-REFERENCE.md#gpu-headroom) for reserve presets, driver limits and user tradeoffs.

The scheduler skips a lower-load efficiency trial when the active Headroom source cap makes the trial's 98% target-delivery requirement unreachable. For example, a 40 FPS source cap cannot qualify 2× output for a 120 FPS target. A cap that tightens during a trial cancels it and restores the retained workload without recording a rejection or delaying later recovery. A nonbinding cap still permits useful trials. This guard consumes the existing cap value; it adds no GPU sampling or pacing owner.

A Headroom cap release can request one expiring efficiency trial even when Fractional has no stable integer rung. The measured source ceiling from before limiting selects a candidate, including a direct 5×-to-2× trial when appropriate; it never establishes acceptance. A low ceiling from a heavy scene still permits one adjacent trial after release, since the current scene may support a faster source. A timing/history reset discards a pending hint. This reuses the scheduler’s lower-load measurement and sustained-delivery acceptance, keeps the qualified workload until success, and rolls back a CPU-limited source or unhealthy delivery. Only explicit Headroom release supplies this hint; ordinary Off workloads retain their previous probe policy.
