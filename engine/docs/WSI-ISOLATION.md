# Gamescope WSI isolation

This guide defines MAKO Renderer's Vulkan-layer discovery and presentation ownership. [HDR pipeline architecture](HDR-PIPELINE.md) owns colour policy; [runtime configuration transitions](RUNTIME-TRANSITIONS.md) owns swapchain replacement and retirement.

The [maintenance checklist](../../MAINTENANCE.md) identifies upstream dependencies and review triggers. [`gamescope-compatibility.json`](../gamescope-compatibility.json) owns protocol provenance, supported wire versions, the last scoped upstream source review, and hardware validation summaries. MAKO uses the system's Gamescope; it does not install or pin the compositor. Wire versions are independent of Gamescope release numbers, and the `_v2` suffix in the factory name is distinct from its negotiated version.

## Maintaining the compatibility record

Run the following commands from the repository root. Keep build pins, source inspection, protocol fixture coverage, and identified hardware results separate. The fixture that advertises version 9 checks MAKO's negotiation cap; it does not qualify a future protocol version.

1. Resolve the candidate upstream ref to a full commit. Compare the swapchain XML and the relevant compositor, WSI, control, focus, or VRR code against the recorded baseline. Record which files and behaviors were actually reviewed; unchanged message names alone do not establish unchanged scheduling.
2. If the incorporated wire contract changes, update the adapter declarations, portable fixture, protocol provenance/hash, third-party notice, and owning guide together. Preserve supported older negotiation paths. A source-only review can advance `last_source_review` while leaving the incorporated protocol provenance unchanged.
3. Run `just check-gamescope-compatibility` and the applicable portable tests in [TESTING.md](../../TESTING.md). To compare all declared request/event names, opcode order, and wire signatures with a locally downloaded copy of the pinned XML, run `python3 engine/scripts/check-gamescope-compatibility.py --upstream-protocol /path/to/gamescope-swapchain.xml`. The supplied file must match the recorded SHA-256. Both checks are read-only and offline; the default check does not fetch upstream or certify runtime compatibility.
4. For a compositor update, compare unchanged MAKO on old/new Gamescope first; compare baseline/candidate MAKO on the same compositor separately. Include private bridge and unbridged controls, optional full WSI when affected, Fixed/Adaptive, fixed refresh/physical VRR, scaling/HDR combinations, serialized/threaded application present waits, pause/menu return, resize/recreation, and the affected native/Proton/Flatpak paths. Select focused Gym suites through [TESTING.md](../../TESTING.md); the relevant boundary determines the required rows.
5. Append a sanitized summary to `hardware_validations` only after inspecting its evidence. Each entry records `date`, `mako_commit`, `renderer_sha256`, `gamescope_version`, `gamescope_sha256`, `gamescope_commit` (null if unavailable), `steam_os_build`, `steam_client_build`, `gpu`, `driver`, `architecture`, `session`, `display`, `vrr`, `protocol_version`, `proton_version`, `flatpak_runtime`, `scenarios`, `result`, `limitations`, and `evidence_reference`. Use null for unavailable or inapplicable environment values and explain material gaps. Keep private inventories, machine/user identities, licensed inputs, logs, screenshots, and generated evidence in MAKO Gym or MAKO Traces; public entries contain only the approved compatibility summary and an opaque evidence identifier.

## Compositor and Vulkan layer

Gamescope has two separate roles:

- The **Gamescope compositor** owns the display session, Game Mode UI, focus, refresh information, composition, and scanout. It remains active.
- The **Gamescope WSI Vulkan layer** joins the application's Vulkan dispatch chain and changes swapchain and presentation behavior. MAKO excludes it from ordinary managed launches.

Disabling Gamescope WSI does not disable Gamescope, Steam, or Game Mode. It changes only the Vulkan layers visible inside the launched process.

## Why presentation needs one owner

MAKO expands one application present into generated present(s) followed by the real frame. If Gamescope WSI sits above a single combined MAKO layer, it observes only the application's original call while MAKO injects additional calls below it. Gamescope WSI therefore cannot pace every delivered image.

When both Scaling and Gamescope WSI compatibility are enabled, the managed path uses this explicit order:

```text
Application / Proton translation
    -> VK_LAYER_MAKO_render
       reconstruction + Frame Generation
    -> VK_LAYER_FROG_gamescope_wsi_x86_64
       sees every generated and real present
    -> VK_LAYER_MAKO_spatial_scaling
       capabilities + physical lower extent
    -> Vulkan driver
    -> Gamescope compositor
```

The lower MAKO role performs no presentation-time GPU work. Reconstruction stays in the upper role so there is one resource and scheduling owner. An FG-only Gamescope WSI compatibility launch uses the upper MAKO role followed by WSI without the lower spatial role.

The legacy timing fallback for ordered SDR through the optional WSI chain uses `VK_GOOGLE_display_timing` only when the lower chain advertises it and the application has enabled neither Google nor EXT presentation timing nor the `presentWait`/`presentWait2` features. Every generated and real output then receives a separate future timestamp from the same bounded timeline used by the isolated scaling bridge. WSI remains the surface/protocol owner; MAKO does not open a second Wayland connection. This Google fallback does not apply to application-owned timing or completion pacing, HDR, unavailable capabilities or the isolated bridge. MAKO drains only its own feedback namespace every 32 outputs, with a count query and at most 128 records per drain, so older WSI implementations cannot accumulate session-length timing history. Failure to read that owned feedback disables this timing path. The optional EXT timing contract described below can supersede this fallback when supported.

The WSI completion-pacing exclusion is decided from the application's device-create feature chain, without changing advertised features or wait calls. A client may wait for its real-frame present ID before producing another source frame; adding MAKO's future timestamp would feed the generated-output lead back into source production. Merely enabling a present-wait extension with its feature disabled does not exclude MAKO timing. Portable retirement tests cover both wait features behind other feature nodes, disabled features, and preservation of the application chain. Real Gamescope qualification still needs serialized and asynchronous clients on both the WSI compatibility path and the private bridge; this policy check does not establish game throughput or input latency.

## Default managed launch

Standalone `mako-launch` and MAKO Decky's generated wrapper establish the normal boundary before `vkCreateInstance`:

```text
VK_IMPLICIT_LAYER_PATH=<private MAKO manifest directory>
VK_ADD_IMPLICIT_LAYER_PATH unset
ENABLE_MAKO=1
DISABLE_LSFG=1
DISABLE_LSFGVK=1
DISABLE_GAMESCOPE_WSI=1
ENABLE_GAMESCOPE_WSI unset
MAKO_DISABLE_HDR_EXPOSURE=1
DXVK_HDR unset
```

The host manifest directory is `<prefix>/share/mako-render/vulkan/implicit_layer.d`; MAKO Decky uses the matching user-local path. Published host packages contain 64-bit and 32-bit MAKO manifests. A prepared Flatpak uses the matching MAKO runtime extension and bounded application overrides rather than the host launcher.

The private path prevents inherited implicit layers from joining accidentally. Known competing frame-generation layers are disabled explicitly. HDR is disabled by default and can be enabled through the isolated surface bridge without admitting full Gamescope WSI. Layer membership cannot be repaired after Vulkan starts, so launchers, manifests, packages, wrapper generation, and Flatpak setup all enforce the same contract.

Standalone `mako-launch` and MAKO Decky apply **Disable Steam Overlay (Restart)** before application startup. This Performance setting defaults to on, disables Steam overlay implicit activation, removes its explicit 32-bit/64-bit Vulkan layers, and filters exact `gameoverlayrenderer.so` basenames from colon/whitespace-separated `LD_PRELOAD` entries while preserving unrelated entries and their order. Off retains the original preload string and the existing Desktop overlay selection. Decky saves the value per profile in its launcher sidecar; Qt saves it globally for `mako-launch` in `launcher.conf`, outside Renderer TOML. The setting may improve smoothness but can affect Steam Input and overlay features. It does not disable the compositor or Game Mode UI. All work stays at launch; diagnostic records report the configured policy and removal count, while process identity reports loaded libraries at Vulkan initialization. Neither record proves that a later runtime has not reinjected the library. Steam Deck/Proton input, overlay, Flatpak and long-session compatibility require real-game validation.

## Guarded Gamescope WSI paths

MAKO Decky admits a staged 64-bit Gamescope WSI payload only when the per-profile **Gamescope WSI (Restart)** compatibility option was enabled before launch:

- With Scaling enabled, the WSI path requires the complete three-role split.
- With Scaling disabled, the WSI path uses the upper Renderer followed by Gamescope WSI.

Scaling alone keeps WSI isolated and uses the existing combined Renderer. The WSI toggle remains independently editable, defaults off, and is not changed by enabling or disabling Scaling. Wrapper regeneration preserves the canonical saved WSI value; old scaling-implied WSI activation is not imported as an explicit opt-in.

With Scaling on and WSI off, `GamescopeScalingSurface` supplies the Gamescope surface association needed to decouple an X11 game's source size from its output size. It creates a real Wayland Vulkan surface for a verified Gamescope XCB/Xlib window and reasserts that window association at every lower present because Xwayland and Steam UI transitions can publish a competing mapping. Each Vulkan swapchain owns a matching Gamescope protocol object and publishes its actual image-count and format feedback at creation; a replacement therefore refreshes the compositor-side swapchain lifetime as well as the Vulkan handle. Combined ordered Frame Generation uses lower MAILBOX only when the driver advertises it and a valid Gamescope refresh clock is known; otherwise it retains lower FIFO. Each generated and real lower present carries its own Gamescope FIFO annotation and distinct future presentation time.

The isolated bridge spaces outputs at the active output ceiling. It negotiates at most version 2 of `gamescope_swapchain_factory_v2` and explicitly uses `create_swapchain_with_timing` when supported. Version-one compositors retain the original constructor and `set_present_time` requests. Binding a newer version alone is not the opt-in, and an unavailable v2 protocol never admits full Gamescope WSI.

On version one, readiness is estimated from Gamescope's existing `past_present_timing` events. A fixed 16-batch ring records owned output IDs, requested times, submission times and readiness lead. The first valid feedback per batch subtracts the presentation margin from the earliest possible presentation, then compares that latch/readiness time with the batch's first deadline. Later feedback can supply the estimate if the first output was dropped, but cannot reduce an estimate already recorded for that batch. Invalid, stale and duplicate feedback is ignored.

Gamescope can defer its readiness observation behind older FIFO outputs. The estimator removes their owned output slots, bounded to one maximum-sized batch, without subtracting spacing already reserved by the deadline twice. Occupancy is captured after submission backpressure and completion dispatch. Matching feedback retires an ordered prefix of owned submission ordinals, including dropped outputs; wrapping protocol IDs and predicted future display timestamps are not occupancy counters. Half the reported presentation margin, capped at half a refresh, remains as a dispatch allowance.

On version two, each `set_present_timing` request carries a nonzero 64-bit serial scoped to its protocol swapchain. The owned `present_timing` report separates compositor-observed queue completion, dequeue/latch and predicted pixel-out. Readiness uses queue completion minus that output's own submission time, with the same first-valid-sample rule and 100 ms bound. It includes dispatch and fence-observation latency, not only GPU execution. If an earlier output was dropped, the later report does not charge CPU spacing between submissions as additional work. Compositor hold time is recorded separately and is never added to GPU readiness or removed using a guessed number of nominal refresh periods. Missing, future, backwards and implausibly old readiness timestamps cannot train the estimate. All-zero reports explicitly acknowledge a dropped output without learning zero work. V2 acknowledgements retire individual outputs because a newer drop can arrive before an older selected output; duplicates cannot retire twice. Forgotten entries expire with the same fixed 16-batch ring. Legacy broadcast timing events are ignored by an opted-in swapchain.

V2 `timing_properties` supplies an effective cycle including the compositor limiter and a fixed panel interval, or `UINT64_MAX` for variable refresh. Valid cycles in the existing 1–1000 Hz range constrain the output ceiling without raising the user's target; fixed intervals provide the local refresh clock. Zero, variable and invalid sentinels do not become numeric rates. These properties are consumed even with diagnostics disabled and do not replace the shared Gamescope VRR preference/focus owner or issue limiter requests. Requests retain absolute monotonic deadlines. The relative and nearest-cycle flags are not enabled: relative first presentation is ASAP, drops change its anchor, and nearest-cycle permits early selection. Neither flag supplies physical display-completion proof. Their adoption needs separate cadence and latency qualification.

For both versions, the largest estimate from four recent batches supplies the lead, bounded at 100 ms. A separate reserve provides one refresh for at most one pending output batch and three for deeper queues, also capped at 100 ms. This reserve does not feed back into the work estimate. A threaded application wait can release source credit while the next batch is pending; its ordered deadlines already reserve those slots, so adding a second refresh of shallow-queue lead can consume the next real frame's work budget. The policy uses owned queue state, without game identity or advertised wait capabilities.

When the existing source cap permits preparation before its return deadline, including an automatic Adaptive cap whose target matches refresh, the bridge accepts that deadline as a per-batch submission budget. It may stage outputs earlier to avoid serializing cap sleep with output spacing, while preserving every protocol display target and the application’s real-frame completion contract. It adds no CPU output clock, future source credit or persistent budget. The policy and its capacity/recovery guards are owned by [Adaptive source-cap preparation](ADAPTIVE-VALIDATION.md#output-timing-within-an-existing-base-cap).

With learned readiness and at most one pending batch, an existing future output slot is retained when the measured work still fits before it. This prevents small CPU return delays after presentation completion from adding another delay to every batch through the one-refresh reserve. The readiness sample records the allowance actually granted. Unknown readiness, deeper queues, the recovery allowance, and work that cannot meet the existing slot retain ordinary rebasing; missed deadlines never create catch-up output. This shared timing rule is independent of FG mode, multiplier, model precision, and VRR preference.

Four refreshes, capped at 100 ms, prime startup and the first increase in admitted batch size. A source gap over one second retires pending feedback, retains the measured cost and largest admitted batch, and saves that estimate until the first generated batch resumes. That batch seeds the existing four-sample window with at least two refreshes of recovery allowance; unknown work still receives the cold-start allowance. Native-only history or relief frames keep learning their own readiness without consuming the saved generated-work estimate or inheriting extra recovery lead. Repeated pauses before generation resumes retain the saved estimate. Native history warm-up cannot trigger a second cold start when the known generated batch resumes. Retaining the largest observed batch also avoids re-priming on every Fractional small/large turn. Backward source timestamps invalidate readiness evidence. Missing feedback keeps the bounded startup allowance. CPU source intervals identify pauses only: they include application waits and MAKO backpressure, so cannot measure GPU cost. The prediction can still miss abrupt workload increases and requires compositor and game qualification. Legacy full WSI retains its existing two-refresh/batch-duration floor. No GPU query, GPU wait or roundtrip is added to the timeline. The connection reader supplies feedback even with diagnostics disabled; acquisition and presentation never poll or read the socket.

The owned timeline also exposes its last scheduled deadline to opt-in Dynamic Cadence Recovery. The scheduler captures that existing horizon only when beginning a native probe and does not evaluate queue-paced source intervals before it clears. Native outputs submitted during the probe do not move its captured boundary. This preserves the bridge's readiness lead and output spacing while avoiding premature rejection of a source that has not yet become observable; no compositor request, GPU query or blocking wait is added. Ordinary unbridged probes and recovery-disabled operation retain their policies.

Unused maximum-multiplier capacity adds no delay. Explicitly disabled Frame Generation (including live 0× with resources retained) removes the generated-batch readiness lead while retaining output spacing and previously queued deadlines; application presentation waits must not turn that unused lead into a two-refresh source limit. Qualified native Fractional Automatic with no effective source cap or a cap at least as high as the target also releases generated readiness lead and follows refresh, allowing native FPS above the Adaptive target while the source pacer continues to enforce any manual cap. Occasional Fractional one-output turns, warm-up and temporary native relief retain the generated timeline. FIFO annotations alone are insufficient: outputs that become ready together can still be discarded. The bounded timeline avoids the extra lower Wayland FIFO callback wait, retains ordering across live target/refresh changes, and rebases after stalls. Adaptive generation follows its target capped at refresh; qualified native Automatic with an absent or target-capable manual cap follows refresh; exact Fixed with an explicit source cap follows cap × multiplier capped at refresh; uncapped Fixed and live generation-off follow refresh. Protocol timing state follows the Vulkan swapchain lifetime, including native fallback after backend initialization failure. Scaling-only retains its existing lower present-mode owner.

The adapter does not load the Gamescope WSI layer or issue its limiter requests. HDR opt-in reuses this owner for colour space and metadata; HDR-off makes no HDR queries or requests. See [HDR handling](HDR-PIPELINE.md). With WSI on, the established WSI chain owns that association and MAKO creates no second connection. With Scaling, HDR and WSI off, no bridge is provisioned. HDR-only needs no scaler or FG backend.

The optional adapter resolves the existing Wayland and X11 client libraries at runtime, requires the active Gamescope session, version 1 or newer of the `gamescope_swapchain_factory_v2` protocol, and window-root server identity, and bounds registry discovery to 500 ms. Every X11-capable Vulkan instance enables the driver Wayland surface extension, including later Wine instances; headless probes and native Wayland instances require no X11 adapter. Missing prerequisites retain the application's original surface and extent safeguards. Surface objects outlive Vulkan retirement, while protocol objects follow Vulkan swapchain creation and destruction; neither a replacement swapchain nor a replacement surface can take over the window before its first present. One event-driven reader belongs to the admitted bridge connection, independently of Mesa’s presentation mode, explicit synchronization, application waits, or focus. It drains the private protocol queue under the existing surface lock, pairs every prepared Wayland read with a read or cancellation, and releases the lock before polling or participating in the shared-reader handshake. A wake FD retries backpressured writes and interrupts idle shutdown; teardown joins the reader before destroying callback data, queues, the display, or client libraries. No periodic polling, per-frame reader wakeup, new connection, or per-swapchain worker is needed. The present path drains already-read events only; it performs no socket polling, roundtrip, dynamically growing timing-history collection, or per-frame protocol allocation.

Session checks run inside the final Vulkan process. Equal or unset `WAYLAND_DISPLAY` permits direct admission. Differing names require a Gamescope socket plus matching device/inode identity or an absent default (`ENOENT`/`ENOTDIR`), accommodating Steam Runtime remapping. Relative paths need `XDG_RUNTIME_DIR`; inherited `WAYLAND_SOCKET`, unrelated/non-socket displays and other lookup failures reject fallback. As in [Gamescope’s socket handling](https://github.com/ValveSoftware/gamescope/blob/master/layer/VkLayer_FROG_gamescope_wsi.cpp), protocol, peer and X11 identity checks still follow. These startup checks cannot provision a disabled bridge.

The adapter preserves X11's concrete window-size contract at both application-facing surface-capability entrypoints: `currentExtent`, `minImageExtent`, and `maxImageExtent` describe the current XCB/Xlib window, including before the first swapchain and after a resize. Only internal driver queries retain Wayland's variable extent for separate scaling output. This applies to every bridged X11 application without executable, engine-name, or version exceptions; exposing Wayland's variable-size sentinel at this boundary can crash applications such as Dolphin during startup. An unavailable or unrepresentable window returns `VK_ERROR_SURFACE_LOST_KHR` instead of fabricated capabilities. Geometry is queried when the application requests capabilities and once at swapchain protocol creation, with no added present-path query or worker. The bridge record identifies `application_surface=x11; extent_contract=window`. Native Wayland, unbridged X11, explicit Gamescope WSI, and existing unsupported-scaling fallback policies remain unchanged.

At swapchain protocol creation, the adapter preserves the application's original source extent separately from the enlarged lower presentation extent. An application extent matching the last capability query or the live window follows the observed window contract. A changed window invalidates those protocol contents for application acquisition; both `vkAcquireNextImageKHR` and the optional `vkAcquireNextImage2KHR` return `VK_ERROR_OUT_OF_DATE_KHR` before a lower acquisition can signal the application's semaphore or fence. An application extent matching neither observation remains an explicit rendering override, because Gamescope can retain the X11 size during such a change. Creation retains its normal Vulkan return codes, previously acquired images remain presentable, and internal generated-image acquisition retains its existing owner. Capability queries propagate later observed changes to the same cached state. The invalidation survives a resize back to the old dimensions and ends with destruction of that swapchain's protocol contents. An explicit nonzero swapchain-maintenance presentation scaling request retains the lower WSI's extent semantics. Acquisition and presentation drain only already-read protocol events; neither performs a geometry query or socket read. A Gamescope `retired` event invalidates the swapchain with `VK_ERROR_OUT_OF_DATE_KHR`, allowing application-owned recreation on the existing surface. A pre-driver rejection still consumes the present waits exactly once and signals supplied maintenance1 fences through empty queue submissions. A broken Wayland connection remains `VK_ERROR_SURFACE_LOST_KHR`. Connection admission rejects failed or malformed peer-credential queries. A visible peer PID must match the X11 Gamescope PID; a successfully queried PID of zero retains the existing protocol/root-property admission for a compositor outside the caller’s PID namespace. Diagnostics identify `capability-query`, `swapchain-create`, and `swapchain-out-of-date` under `spatial scaling window extent`, with the queried, original application, live window, and physical presentation sizes. The creation record distinguishes `extent_contract=window`, `application-override`, and `presentation-scaling`.

The Gamescope WSI option is independent from Scaling and the mutually exclusive MangoHud/vkBasalt selection. Both full-WSI configurations remain SDR-only in managed launches; HDR uses the isolated bridge. MAKO Decky validates the host manifest identity, library, architecture, and activation gates, then copies only that payload into its managed compatibility directory. It never exposes the full host implicit-layer directory. Standalone `mako-launch` applies the same MangoHud identity, architecture, and gate restrictions, staging named host manifests in a private cache only when explicitly requested. Qt shares Decky’s per-profile external-layer selection and emits the corresponding launch environment; neither UI permits simultaneous MangoHud and Shaders. See [MangoHud launch policy](LAYER-CHAINING.md#standalone-mako-renderer-with-mangohud).

The optional full-WSI launcher's eligibility requires `GAMESCOPE_WAYLAND_DISPLAY` to be nonempty and `WAYLAND_DISPLAY` to be empty or equal to it before the runtime starts. Desktop Mode, a mismatched nested Wayland session, or unavailable staged manifests leave WSI disabled and use the combined Renderer. That path retains its own extent checks and can remain native if the game cannot supply a distinct source size. Once a split chain is selected, missing lower-role evidence fails closed; it cannot silently become a combined chain after Vulkan starts.

The managed wrapper sets the semantic prefix through `VK_INSTANCE_LAYERS`; manifest-directory enumeration does not define order. When Scaling and WSI are both selected, the order is render role, Gamescope WSI, spatial role, then any selected post-process tool. Caller-requested layers follow that managed prefix. See [Optional graphics integrations](LAYER-CHAINING.md) for supported exceptions.

Prepared 64-bit Heroic and EmuDeck Flatpak launches can receive the same bounded WSI payload and MAKO extension. Unprepared Flatpaks, 32-bit WSI presentation, HDR, broader host layouts, and other sandboxes are separate validation boundaries.

## Scaling ownership proof

Gamescope WSI may replace the surface handle between upper and lower roles. Fixed-surface capabilities and create decisions therefore cross the two MAKO DSOs through same-thread, one-shot relays tied to the physical device and request. The lower decision is authoritative: a valid source/presentation split activates scaling, while an equal-extent decision creates a native context. Missing, stale, or mismatched evidence rolls back the create.

Call order alone is insufficient. The lower spatial role must observe a surface created through `vkCreateWaylandSurfaceKHR`, proving that Gamescope WSI converted the application's X11 window into the compositor-owned surface. An XCB or Xlib surface at that boundary remains native with `inactive_reason=gamescope-wsi-surface-unproven`; the upper role can still retain Frame Generation. Direct combined Renderer operation has no intervening WSI owner and does not require this split-only proof.

For variable surfaces, scaling through either the managed split chain or the isolated surface adapter also requires the positively identified Gamescope output target. A missing target or a source with no enlargement headroom remains native. [Spatial scaling architecture](SCALING.md) owns the full fixed/variable extent policy.

## Presentation and swapchain policy

`PresentationEnvironmentPolicy` resolves WSI isolation and HDR exposure once at process start. `selectPresentationTransport()` then selects one immutable swapchain transport:

- `OrderedSdr` for the supported managed SDR path.
- The isolated HDR bridge retains `OrderedSdr` and its existing ordered scheduling; its name does not imply SDR pixels.
- `GamescopeHdr` only for the experimental combination of Gamescope, WSI, allowed HDR exposure, and an HDR-capable swapchain.

Current launchers select `OrderedSdr`. It owns FIFO ordering for generated and real frames and removes Gamescope's incompatible present-mode override from the lower create chain. Unknown create-chain prefixes fail before driver creation rather than mutating caller-owned data.

Frame Generation normally reserves lower WSI images for the largest configured generated batch. FG-only ordered presentation also requests its established relief headroom; combined scaling that is active or configured above 1.0 uses a smaller bounded topology for compatibility. An enabled 1.0 scaler remains inactive and retains the FG-only relief topology. Surface limits remain authoritative, and an initialization or memory failure retries once with the application's original minimum.

Eligible capped Fixed and Adaptive profiles can prepare outputs during the existing source-cap wait, including on admitted scaled and variable surfaces. Direct transport without an output-timing owner can space outputs within that interval; the isolated bridge and Renderer-owned Google or EXT timing retain their own output clocks. The application still returns no earlier than its original cap deadline. See [output timing within an existing base cap](ADAPTIVE-VALIDATION.md#output-timing-within-an-existing-base-cap) for automatic-cap eligibility, image-capacity and admission-pressure guards, fallback behavior, and required source/output evidence.

Adaptive ordered delivery preserves the established sequential acquire/present cadence and adds an explicit adapter only for VRR. Fixed refresh retains the 3.3 ordered generated-image acquire, including MAKO Decky's 50 ms application-present ceiling, so ordinary FIFO image release on Steam Deck and other non-VRR devices is not misclassified as failed generated load. Requested or active VRR uses the same finite ceiling because lower-image release is not locked to a fixed output-period ladder. A shorter explicit ceiling always wins, and the boundary cannot recursively expand when MAKO's own wait reduces observed source FPS. If VRR transport still cannot supply the next image, MAKO stops that generated delivery, drains the already scheduled backend timeline, preserves the real frame, and moves following frames to zero-wait admission before backend work. Generated delivery resumes as soon as a complete batch is available, but zero-wait preflight remains armed until consecutive complete batches account for one returned-image turnover; a single available frame cannot repeatedly re-expose gameplay to the bounded wait. The turnover proof derives only from the lower image count and generated batch size, so it does not change across 60, 90, 120, or higher refresh rates. One VRR hold therefore cannot become a long scheduler backoff or a repeated bounded stall. Headroom-tight batches remain zero-wait preflight so they cannot reserve work they cannot deliver. Fixed keeps sequential ordered delivery because its multiplier is an explicit workload selection. When the returned pool fits that Fixed batch beyond the application's minimum, no additional relief image is required; without relief, acquisition has a shared ceiling of 50 ms per application present, reduced by any shorter configured ceiling. The legacy full-WSI `GamescopeHdr` transport remains nonblocking.

**Game Swapchain Images (Restart)** is the per-profile escape hatch for games that reject MAKO's normal reservation. It preserves the application's requested minimum from the first managed create and every replacement. It is off by default, process-static, and never enabled by executable or runtime heuristics. With no reserved headroom, synthetic output can be skipped when the compositor has no free image.

Changes that need a new source/presentation pair use the game-owned recreation and safe-retirement rules in [Runtime configuration transitions](RUNTIME-TRANSITIONS.md). MAKO never destroys an active application swapchain merely to apply a profile setting.

## Transport boundary and evolution

MAKO owns the Renderer graph: spatial scaling placement, generated-frame planning, synchronization, recovery, and resource lifetime. The launcher and Decky wrapper select the optional vkBasalt layer's position in the Vulkan chain; vkBasalt owns the order and execution of its selected effects. Gamescope remains the authority for compositor state such as the presentation target, refresh, focus, HDR output state, and VRR policy. The combined Renderer consumes only the Gamescope state and protocol operations required by its selected path; it does not delegate MAKO's scheduling decisions to the compositor.

The current deployment paths already follow this ownership model: ordinary managed launches use MAKO's ordered SDR transport with Gamescope WSI isolated, the optional scaling surface adapter supplies the minimum verified Gamescope association and swapchain feedback needed for combined scaling, and the guarded Gamescope WSI profile provides a compatibility or split-scaling path. Gamescope WSI remains opt-in because it adds another presentation owner and is not available across every architecture, sandbox, session type, or host version.

If transport-specific behavior grows, keep it behind explicit internal direct, Gamescope-native, and full-WSI compatibility boundaries selected from proven startup capabilities. Scheduling must remain above those boundaries. This separation does not by itself improve quality, latency, or performance; its value is containing compatibility failures to one transport, making each path independently testable, and allowing a Gamescope integration to change without rewriting scaling, layer-chain, or Frame Generation policy. Do not create parallel scheduling implementations merely to name these boundaries.

## Gamescope timing capabilities across the stack

The protocol declarations follow [Gamescope commit `2b5cf191`](https://github.com/ValveSoftware/gamescope/blob/2b5cf191d1047d6895516a834de8a72ac1c342f3/protocol/gamescope-swapchain.xml). Its [timing implementation changes](https://github.com/ValveSoftware/gamescope/commit/77f3d88a2c14b1e064bb3ec52380bfb46560b0b7) refresh the VRR prediction during compositor processing, wake held presentation targets and protect FIFO ordering when fences signal out of order. Those compositor fixes require a compositor containing them; updating MAKO cannot retrofit them into an older Gamescope. Version/capability negotiation remains authoritative, independently of a distribution's package label.

| Path | Information and pacing owner | New capability boundary |
| --- | --- | --- |
| Direct X11 or native Wayland, no bridge | Driver WSI owns image release; MAKO consumes shared Gamescope refresh, VRR and focus feedback and its existing Fixed/Adaptive policies. | Advertised Vulkan timing can supply calibrated queue completion and refresh properties. Unsupported drivers retain ordinary pacing; no private protocol connection is added. |
| Private bridge v1 | MAKO owns FIFO annotations, absolute output targets and bounded legacy readiness estimation. | Existing compositors keep their supported contract, including wrapped-margin decoding. |
| Private bridge v2 | The same owner gains per-output reports, distinct queue/latch stages, explicit drops and swapchain-local timing properties. | Requires the advertised v2 factory and opt-in constructor; does not enable Gamescope WSI. |
| Optional full Gamescope WSI | The lower WSI layer owns the protocol. MAKO prefers supported Vulkan EXT timing, with negotiated Google timing as fallback. Application timing and enabled presentation waits retain ownership. | Both the compositor and WSI binary must expose the new capability. The SteamOS-supplied version continues using its supported contract. |

Shared VRR pacing, source caps, output planning, pressure recovery and Steam focus handling must be qualified across these paths. Readiness policy is transport-specific: a direct image release, a legacy predicted refresh and a v2 observed queue completion are not interchangeable measurements. Bridge timing reuses the connection’s event-driven reader and adds no GPU query, synchronous roundtrip or socket read on presentation. Legacy full WSI retains its fixed batch lead and bounded feedback drain. When a non-bridge surface advertises the complete `VK_EXT_present_timing` contract, MAKO can instead learn from its own calibrated queue-completion timestamps; legacy predictions are never substituted for those observations.

Non-bridge EXT timing requires advertised `VK_EXT_present_timing`, `VK_KHR_present_id2` and calibrated timestamps, enabled device features, and surface support for absolute targets, present IDs and queue-operation-end queries. MAKO never takes an application-owned timing or present-ID namespace, never duplicates caller feature nodes, and never enables presentation waits. Each eligible FIFO swapchain owns 64 feedback reservations and a monotonic ID stream. One bounded query per source batch retires complete records; full storage stops requesting new records while preserving target-only presentation. Missing commands, unsupported clocks, excessive calibration uncertainty, timing-property errors or query failure retain existing pacing. A temporary `VK_NOT_READY` property result clears stale limits and retries once on the next source batch, using only an independently known refresh clock until properties arrive. Losing the feedback transport restores the legacy preparation lead while preserving queued output deadlines; a clock change with a working transport only invalidates learned readiness. Advertised timing alone cannot take pacing ownership without a usable refresh clock, so missing refresh information retains direct source-cap output pacing. Local clocks are calibrated against the host monotonic clock at startup, on domain changes and at most once per second during use; changed clocks invalidate learned readiness without moving ordered output targets. Timing properties distinguish the effective cycle from fixed panel refresh. Only the observed queue-completion stage trains preparation lead; display predictions and application wait durations do not. No compositor installation or update is performed by MAKO.

Qualify changes with unchanged MAKO against old/new Gamescope first, then baseline/candidate MAKO against the same compositor. Include direct and full-WSI controls, Fixed and Adaptive, at-refresh and below-refresh targets, serialized/threaded present waits, asynchronous GPU work, cold startup, VRR toggles and Steam UI return. Measure source cadence separately from output cadence: a serialized real-frame wait at a fractional source/output ratio can expose output-cycle quantization, and source-cap preparation never completes that wait early. Nested root-property transitions prove policy handling, not physical VRR. Physical qualification still needs matched scenes, output completion/visible-frame evidence and latency observations; neither the v2 pixel-out prediction nor installed Gamescope's ordinary presentation feedback establishes those by itself.

## Private bridge presentation-wait compatibility

Application `presentWait` and `presentWait2` capabilities and enable requests pass through unchanged. The bridge's earlier feature-negotiation fallback helped Halo but regressed Witcher 3; choosing a translation-layer fallback is not a common pacing solution. The bridge instead estimates its own readiness from compositor feedback, without treating CPU frame arrival as GPU cost. On protocol v1, Gamescope encodes the prediction-minus-latch margin as an unsigned 64-bit difference; when VRR latches after a stale prediction, this wraps. The bridge recovers the latch with unsigned subtraction before validating the clock range and owned-batch readiness window. A negative margin contributes no extra dispatch allowance, while ordinary positive margins retain their existing treatment. V2 uses the separately reported queue-completion stage described above. Invalid timestamps still retire matched completion without supplying readiness evidence. No game-name exception or configuration setting selects this policy.

This applies to every isolated bridge using generated ordered output, including a bridge provisioned by HDR with Scaling off and an SDR swapchain created by an HDR-enabled launch. It changes presentation timing, not HDR encoding, colour conversion, metadata, shader passes or generated-frame planning. Explicit FG-off retains ordered deadlines already queued and adds no generated readiness lead. With Scaling and HDR off, no isolated bridge is provisioned. This bridge-specific wait rule does not apply to unbridged FG, native Wayland/Desktop or full Gamescope WSI; their timing capabilities are described above.

The real application's present ID remains on its real image. Waits retain the driver's timeout, completion and error semantics; neither an earlier generated output nor CPU submission is reported as real-image completion. Qualify this policy with serialized and concurrent application waits, asynchronous GPU work, HDR bridge controls, and independent compositor-completion observations. Compare games with the same Frame Generation mode, VSync, VRR, scene and source/output resolution. Repeated Gamescope timing predictions do not alone establish dropped frames; physical VRR, unique visible outputs and input latency require separate evidence. Pause qualification distinguishes bounded native-only history rebuilding from uninterrupted generated output. Require continued real-frame delivery and prompt return to the generated cadence; preserve the full recovery metrics rather than hiding the native interval in a settling phase. Successful portable tests alone do not establish these properties or throughput.

## Supported concurrency boundary

Renderer interception state currently supports one active Vulkan instance dispatch domain per process. Applications must externally synchronize each `VkQueue` as Vulkan requires. Multiple swapchains can exist in that instance, but a `VkPresentInfoKHR` batch containing more than one swapchain is rejected when any entry is managed by MAKO; shared binary waits and per-swapchain extension arrays do not yet have a safe fan-out owner.

Do not claim general multi-instance, multi-queue, or multi-swapchain-batch support until the state is instance/queue-owned and real-hardware coverage exists.

## Diagnostics and validation

### Steam focus feedback

The existing background Gamescope reader samples `GAMESCOPE_FOCUSED_APP` (input recipient) and `GAMESCOPE_FOCUSED_APP_GFX` (displayed application) from the verified same-compositor server-zero root. Launch identity is resolved once at process startup. A valid `UMU_STEAM_GAME_ID` takes precedence because UMU preserves Steam's launch identity there before replacing the ordinary IDs with its store identity or prefix hash. Otherwise, MAKO uses the first valid `SteamAppId`, `STEAM_COMPAT_APP_ID`, or `SteamGameId`. App-ID fields require a complete nonzero unsigned 32-bit number other than Steam UI's 769. Game-ID fields accept a plain Steam app or a packed type-2 shortcut with an empty app field and a high-bit-set shortcut identity in the upper 32 bits; malformed, overflowing, mod, and P2P IDs are rejected without truncation. This supports Steam games and non-Steam shortcuts, including Heroic/UMU, without rewriting the game's environment or inferring identity from cache paths.

Matching game input/display means gameplay focus, and Steam input over this game or Steam's own display means Steam UI focus. Another app, missing/empty/malformed properties, an unknown launch identity, changed compositor identity, or stale feedback is unknown, never guessed from FPS. Graphics identity is re-read to reject a transition during the sample; focus changes require 250 ms agreement. The monitor records returns even when the game submits no frames. Consumers expire cached focus after one second and perform no X11 queries on the presentation thread. The resolved identity feeds the same suspension and return policy across Fixed, Dynamic Cadence Recovery, Steady Adaptive, and Fractional Adaptive, independently of multiplier, scaling, and Gamescope WSI selection.

This observes Steam UI ownership, not a particular menu's identity or the game's own pause screen. Very short visits can be missed by the existing 250 ms sampling cadence. Notifications that leave input on the game do not interrupt generation. Desktop, unsupported launchers, sandbox access restrictions, and unrecognized Steam focus layouts retain ordinary scheduling without menu-authorized rebuilds. Steam, Quick Access, Decky panels, keyboard, full overlay, brief taps, focus switches, and stale/missing feedback still require real-session validation; portable tests do not prove every client version's behavior. No Gamescope WSI layer or per-frame Decky RPC is required.

When presentation diagnostics are enabled, the private bridge correlates the negotiated protocol's timing events with at most 128 pending requests per swapchain and reports aggregates at most once per second. The connection reader drains timing events regardless of diagnostic enablement, so an idle application or a driver that does not read this connection cannot leave compositor feedback accumulating. Diagnostic aggregation adds no socket read, roundtrip, worker, or presentation-policy input. Disabled diagnostics allocate no timing history. Gamescope-reported target-vblank and v2 pixel-out timestamps are predictions, not physical scanout measurements.

Application VSync diagnostics preserve the pre-filter dynamic present mode and pass application presentation waits through unchanged. Optional KHR/KHR2 wait hooks are exposed only by the application-facing frame-generation/combined role when the lower command exists and diagnostics are enabled; the lower spatial role forwards them without a second observation. The hooks do not enable extensions or fabricate completion. A bounded per-thread accumulator reports stable-stream wait duration and result counts at most once per second. Bridge feedback separately distinguishes repeated/backwards predictions from nonconsecutive IDs. These observations are not scheduling inputs or physical scanout evidence.

### Interpreting presentation records

`operation=gamescope-bridge-timing` summarizes requested and compositor-reported intervals, CPU submission lateness and reported lateness relative to requested timestamps. `feedbacks`, `outstanding`, `unmatched`, `overwritten` and `discontinuities` describe coverage or rejected feedback; interval samples require consecutive IDs. Zero feedback is unavailable evidence. `nonconsecutive_ids`, `repeated_timestamps` and `backwards_timestamps` can overlap, while `discontinuities` counts each unusable interval once. `late_latch_feedbacks` counts matched feedback with a decodable latch later than its predicted refresh, exposing wrapped negative margins; it does not prove that the separate owned-batch readiness bounds accepted the sample. These counters are not frame-drop counts, and predicted target vblanks do not establish physical scanout or input latency.

`timing_protocol=1|2` identifies negotiation and `timestamp_kind=prediction` labels reported display times. On v2, `dropped` counts explicit all-zero reports, separately from selected/partially reported `feedbacks`; `queue_ready_*` measures submission-to-observed-queue-completion and `compositor_hold_*` measures queue-completion-to-latch. `invalid_stages` rejects inconsistent clock/order evidence, while `unavailable_stages` records missing timestamps. Neither supplies a readiness sample by itself. `refresh_interval_ns=18446744073709551615` denotes variable refresh. Legacy records and v1 retain their existing fields; zero stage samples on v1 are unavailable evidence, not zero GPU work.

`operation=gpu-headroom` records the selected reserve, target utilization, whole-device utilization average, effective Headroom source cap, real-frame floor and controller state. Every collector preset retains these records. `telemetry-unavailable` means the extra cap was released; `frame-rate-floor` means further reduction is constrained. Utilization includes other applications on the same GPU and is not per-game GPU time or power. The [controller contract](ADAPTIVE-VALIDATION.md#gpu-headroom) owns sampling and response; [collection steps](COLLECT_DIAGNOSTICS.md#gpu-headroom-evidence) describe an Off/On comparison.

`operation=adaptive-efficiency-probe-cancelled reason=gpu-headroom-source-cap` means a live Headroom cap made an active lower-load trial unable to meet its target. The retained workload resumes without a failure cooldown. Every collector preset retains this cancellation; it is not a GPU or presentation error.

The initial `presentation timing initialized` record identifies optional Renderer-owned `VK_EXT_present_timing` support on a non-bridge surface. `active=0` means initialization retained existing pacing; a later `presentation timing fallback` record means feedback or clock support became unavailable. Support depends on the installed driver and WSI capabilities described [above](#gamescope-timing-capabilities-across-the-stack); MAKO does not update Gamescope.

`operation=application-present-mode` records the application's original mode before dynamic overrides are filtered, initially and on changes; ambiguous multi-swapchain overrides report `-1`. `operation=application-present-wait` summarizes calls to `vkWaitForPresentKHR` and, when supported by build headers, `vkWaitForPresent2KHR`, retaining call/result/poll counts, present-ID bounds and mean/maximum blocking duration. The optional `first_failure_result`, `first_failure_present_id`, `first_failure_timeout_ns` and `first_failure_duration_ms` fields retain the first timeout/error's result, present ID, requested timeout and actual duration, so an error is not inferred from an unrelated window maximum. Successful windows omit them; older builds do not record them. Each thread emits at most one window per second for a stable device/swapchain/API stream. Switching streams drops the partial window; the final partial window is not flushed. No record means unobserved or shorter-than-window activity, not proof of no wait. Join wait records by PID and swapchain independently of the presentation thread. Diagnostics disabled bypasses these wrappers entirely.

The `scaling` and `performance` presets retain all three operations. Every preset retains the initial Gamescope VRR/Allow Tearing snapshot, live pacing-owner changes and scaling window-extent records. `recovery` and `performance` also retain Gamescope focus changes and legacy recovery records. Use `mako-diagnostics --list` for the complete preset list; [Collect diagnostics](COLLECT_DIAGNOSTICS.md) contains only the user collection steps.

Every preset also retains Renderer failure headers with up to eight adjacent exception-detail lines folded into the same record; additional details produce `error_details_truncated=1`. The collector recognizes unprefixed libwayland protocol errors, including `#`/`@` object IDs and destroyed proxies, both directly and under Steam's `[YYYY-MM-DD HH:MM:SS]` timestamp prefix. This preserves the reported cause of a compositor disconnect without admitting ordinary Wayland traces or unrelated game output. The source must be the original session log: an older filtered report may already have discarded these details. Errors the client never read or logged cannot be recovered, and the separate Gamescope system journal is outside this collector's input.

### VRR and tearing feedback

The same background reader samples Gamescope's explicit server-zero `GAMESCOPE_VRR_ENABLED`, `GAMESCOPE_VRR_CAPABLE`, `GAMESCOPE_VRR_FEEDBACK`, and `GAMESCOPE_ALLOW_TEARING` properties. Requested, connector-capable, and currently active VRR remain separate facts because an overlay can temporarily stop adaptive scanout without changing the user's setting. An explicit active signal, or enabled VRR on a connector not explicitly marked incapable, selects VRR-aware pacing. Missing properties on older Gamescope builds preserve the established fixed-refresh behavior; after a valid value has been observed, a missing or malformed individual read retains that value instead of flapping pacing ownership.

The optional per-profile Gamescope VRR choice is owned by the MAKO launch helper, outside the Vulkan present path. It requires `gamescopectl`, `xprop`, and a working systemd user service, so the watcher survives the game's process group; without them, it leaves VRR alone. It checks the active display's `gamescope_control` `supports_vrr` flag before changing Gamescope's live `GAMESCOPE_VRR_ENABLED` root property. Unsupported displays and missing capability information leave VRR untouched, including when a saved profile selects On or Off; this check follows the active connector rather than a device model. The helper finds the server-zero root belonging to this game's Xwayland Gamescope PID and uses that same property for both the request and readback. Gamescope consumes changes to the property as its adaptive-sync preference; a console-variable write alone need not update the property. An unverified display or missing VRR value prevents a write. After a matching Renderer runtime status appears with Frame Generation enabled, the helper can apply the requested value. Its one-second game/profile loop checks the live root value every five seconds while a confirmed choice is stable, avoiding a subprocess on every loop; profile changes and exit restoration still read the live value immediately before writing. It retains the starting value after an unverified write so it can still restore a later confirmed change. It restores the observed value when the game ends only if that value is still MAKO's request, and it never restores into a replacement Gamescope session. If Steam changes the live value during play, the helper yields at its next root-value check until the MAKO profile choice changes. Gamescope's VRR setting is session-wide, so Steam's Game Mode toggle and this choice cannot be fully independent. A Steam change that writes the same live value as MAKO's request is indistinguishable from no change; MAKO can only detect a value change. No persistent Steam setting is written.

For Flatpak games, MAKO Decky starts the same installed helper in host discovery mode (`--watch-flatpak`). It polls the existing runtime-state directory once per second, starts leases only for enabled contexts requesting On or Off, bounds the inventory to 64 records, and resolves namespace PIDs through the kernel-held publisher lock, matching UID, start tick, and namespace PID. The game’s Gamescope socket peer must match its Xwayland Gamescope PID before an existing detached per-game lease can start. Only display/session variables are imported; no sandbox permissions or arbitrary game commands are granted. Discovery retries unavailable or terminated leases every 30 seconds. Decky reload stops discovery but leaves detached leases to restore their own game session. Native launch leases retain their existing path. Standalone Flatpak launches need this helper running on the host as the same user; a helper inside the sandbox cannot control the host session.

The detached helper records `Gamescope VRR lease decision=...` only when its decision changes, including missing game context, unsupported or unknown display capability, unverified Xwayland identity, unavailable root-property readback, unverified writes, and an already matching live value. A `write-confirmed-on` or `write-confirmed-off` decision follows a successful root-property readback; `already-on` or `already-off` means MAKO made no write. Separate applied, restored, and external-change records distinguish ownership from Gamescope feedback observed by MAKO Renderer. On exit, restoration retries up to five times while the original Gamescope session remains available, then records `restore-unverified-at-exit` and fails the transient service instead of holding its session lock indefinitely; the user may need to restore VRR through Steam if readback remains unavailable. These helper records go to the transient systemd user-service journal, not the game's presentation-diagnostics log; after returning to Desktop Mode, inspect them with `journalctl --user -o short-iso | grep -F 'MAKO Renderer: Gamescope VRR lease'` alongside the game's timestamped Renderer diagnostics.

This feedback selects the pacing clock, whether a validated higher Steady Adaptive rung requests its full generated batch under FIFO, and whether an already accepted constant Fractional rung hands pacing to FIFO. A confirmed VRR enabled-preference change can also refresh a rejected higher-load retry under the bounded [Adaptive retry policy](ADAPTIVE-VALIDATION.md); active-only overlay changes preserve rejection history. It does not itself promote a multiplier, qualify Adaptive work, start recovery, or request swapchain recreation. Applied 3x–5x FIFO or automatic integer caps separately verify delivered output through the shared [Adaptive workload policy](ADAPTIVE-VALIDATION.md#measuring-applied-integer-pacing), including target preference and below-target real-FPS cost checks. Recent promotions retain a bounded adjacent baseline; delayed handoffs obtain a fresh lower-load sample through the existing efficiency probe. Planned probe release and return do not create another handoff-validation loop or failure cooldown. Interrupted pacing evidence is discarded rather than treated as transport failure. `GAMESCOPE_ALLOW_TEARING` is diagnostic transport context only: ordered SDR still owns FIFO delivery, so the Steam toggle does not replace MAKO's effective present mode. The incoming application present mode and effective transport mode are both recorded at swapchain creation. Sampling remains off the presentation thread and performs no per-frame X11 or Decky query.

For the behavior of each Fixed, Steady Adaptive, and Fractional Adaptive pacing path under VRR and fixed refresh, see [VRR and fixed-refresh pacing paths](ADAPTIVE-VALIDATION.md#vrr-and-fixed-refresh-pacing-paths).

### Presentation evidence

For a default HDR-off managed launch, loader and Renderer evidence must agree that Gamescope WSI is isolated, HDR exposure is disabled, the render role selected a profile and backend, and ordered SDR presentation owns delivery. The presentation-feedback record must identify the explicit VRR state and selected pacing owner when those properties are available. For an FG-only compatibility launch, `VK_LAYER_MAKO_render` must be above the architecture-correct Gamescope WSI identity. For scaling with WSI, the complete three-role order, lower Wayland provenance, authoritative create relay, active source/presentation split, one upper reconstruction owner, and correct generated/real delivery are all required.

Scaling with WSI off must instead prove a combined Renderer context with WSI isolated, no lower spatial role, and an active source/presentation split. WSI on/off comparisons must retain the same source/output sizes, scaler, FG mode, scene, and refresh rate; a safe native fallback cannot count as improved scaling performance.

For X11/Proton scaling through the isolated surface adapter, additionally require `spatial scaling surface bridge` with `transport=wayland; gamescope_wsi=isolated` and Wayland surface provenance. The `spatial scaling surface formats` record reports native X11, private Wayland, and shared format counts; `action=intersection` means the application sees only shared pairs in its X11 order, while `action=wayland-fallback` means no common pair was proven. A lower layer may omit the global instance-extension entrypoint (Gamescope WSI) or return `VK_ERROR_LAYER_NOT_PRESENT` (vkBasalt). Either case triggers a global query through the existing Vulkan loader owner; successful layer queries and other errors retain their original handling. A complete list must confirm Wayland support before bridge admission, and optional maintenance1 retirement requires both the instance surface dependencies and the device feature. Missing dependencies, incomplete lists and other enumeration failures retain the natural presentation fallback. The query runs at instance creation, never on presentation, and does not enable the full Gamescope WSI layer. MAKO Gym's `run-proton-end-to-end.sh --scaling-surface` exercises this boundary inside Steam Linux Runtime with the existing translation matrix. Its default mode still validates the full WSI split chain. Commercial-game, other-driver, 32-bit, and Flatpak evidence remains separate.

Use `VK_LOADER_DEBUG=layer` only for a short reproduction because it is verbose. Presentation diagnostics are also opt-in and can affect timing. Use `mako-diagnostics --list` to select focused `layers`, `startup`, `scaling`, `performance` or `recovery` reports; [Collect diagnostics](COLLECT_DIAGNOSTICS.md) gives the standard collection steps.

Any discovery, ordering, present-mode, pNext, image-reservation, or transport change needs its portable launcher/wrapper/package/Flatpak contracts plus applicable MAKO Gym Gamescope, native Vulkan, Proton, synchronization, recovery, and runtime-family evidence. Loader success or `vkcube` does not prove real-game pacing or image correctness. Record untested architectures, sandboxes, GPUs, drivers, and hardware paths explicitly.

Present-chain filtering also preserves `VkPresentTimingsInfoEXT` (`VK_EXT_present_timing`) when a newer application or Proton runtime places it before a removed maintenance1 mode override or scaling damage region. `FilteredPresentPNextChain` in `mako-render/src/pnext_chain.hpp` copies the complete outer timing node and retains its caller-owned timing array, present IDs, fences, and untouched suffix. The fixed ABI layout remains recognized when MAKO is built with older Vulkan headers, with compile-time layout checks against SDKs that expose the extension. This does not disable the extension, rewrite timing values, change which output owns application-present metadata, or weaken rejection of unknown prefix structures. `pnext-chain` tests cover immutable input, interleaved removals, null timing arrays, passthrough, and unknown-node rejection.
