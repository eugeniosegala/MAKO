# Native installation transactions

This is the implementation reference for atomic file replacement and rollback during native MAKO Renderer installation. It covers MAKO Decky and the standalone archive installer so agents and maintainers can change either path without weakening the shared installation contract. User instructions remain in the [Renderer README](engine/README.md#installation) and [Decky README](plugin/README.md#what-it-manages).

## Contract and limits

Both installers prepare replacement files separately from their destination and retain previous files until the native installation succeeds. Each destination replacement is atomic; the complete installation is a sequence of replacements and removals with rollback. A reader can observe files from different generations during that sequence. `active-renderer.json` records the selected owner/version after the payload work; it is not a filesystem-wide commit pointer used to gate all readers.

| Property | MAKO Decky | Standalone archive |
| --- | --- | --- |
| Replacement primitive | Adjacent staged file, then `Path.replace()` | Adjacent `replacement` file, then `mv -fT` |
| Previous regular file | Adjacent hard link, falling back to `shutil.copy2()` | Adjacent `cp -Pp` copy |
| Previous symlink | Recreate the link itself in the backup directory | Preserve the link itself with `cp -Pp` |
| Failure recovery | Catch `BaseException` inside `managed_install_transaction()` and restore in reverse order | `EXIT` cleanup restores in reverse order while replacing and not committed; `HUP`, `INT`, and `TERM` exit through that cleanup |
| Native success boundary | Normal exit from the transaction context after both identity writes | `install_committed=1` after every destination operation |
| Configuration | `conf.toml` participates in rollback | Installation leaves configuration alone |
| Durability | Flush and `fsync()` each staged output before rename; no parent-directory fsync or durable transaction journal | No explicit fsync or durable transaction journal |

Neither path provides automatic recovery after power loss, `SIGKILL`, or another termination that prevents cleanup from running. Current native install and uninstall entry points acquire a nonblocking exclusive `flock` on `$install_prefix/.mako-render-install.lock`; Decky uses `~/.local` as that prefix and assigns the lock to the real user when running as root. Explicit Decky Renderer removal acquires the same lock before restoring Remote Play or stopping discovery. Cancelling its RPC waits for an ongoing restoration worker before releasing the lock and preserves Renderer files. The zero-byte lock is retained as a stable inode after removal and released before standalone UI startup. Management-tool startup repair uses this lock; other startup migrations, configuration writers, direct development deployment, and older installer versions do not. Close games using MAKO and stop configuration edits during installation. Per-file replacement avoids truncating an existing mapped inode, but does not coordinate game launch or writers outside this lock.

The rollback set consists of explicit file paths. It does not restore the directory tree, undo unrelated writes, or coordinate with another process. Directories created during preparation can remain after failure. Temporary files and backups normally disappear on completion; cleanup errors are reported and can leave artifacts.

## Shared native selection and identity

At the default user-local prefix, Decky stores libraries under `~/.local/share/mako-render/lib{,32}/`; the standalone archive stores them under `~/.local/lib{,32}/`. Both installers supply shared manifests under `~/.local/share/mako-render/vulkan/` and `~/.local/share/vulkan/implicit_layer.d/`, selecting the installed libraries for the launch workflows. Both binary locations can remain present after switching owner. Only the standalone archive registers its spatial-scaling layer in `~/.local/share/vulkan/implicit_layer.d/`; Decky's wrapper uses the private scaling manifests, so a Decky installation retires those public registrations instead of leaving them on the previous payload.

| Record | Meaning |
| --- | --- |
| `~/.local/share/mako-render/installed-engine.json` | Decky's installed archive name, version, SHA-256 and architecture descriptors; can describe an inactive Decky payload |
| `~/.local/share/mako-render/active-renderer.json` | Schema-1 selected native identity: `owner` is `decky` or `standalone`, with `version` and optional `payload_sha256hash`; Decky also writes its archive `sha256hash` |
| `~/.local/share/mako-render/flatpak-runtimes.json` | Schema-1 record, per Freedesktop branch, of the Flatpak runtime commit and bundle SHA-256 that MAKO Decky last installed; a branch is removed with its runtime |
| `~/.local/share/mako-render/installer/installed-files.sha256` | Standalone relative-path ownership record, with hashes of installed content after desktop-entry rewriting |

`InstallationService._active_manifest_owner()` resolves the private Frame Generation manifest's library path to determine which managed payload it selects. `check_installation()` checks agreement with the selected owner, required files, host support and wrapper presence before reporting installation/update state; an identity file alone is insufficient. Decky's generated wrapper, Flatpak VRR discovery, model inspection, and shader editing use helpers from that selected owner, mapped from the same manifest resolver. They do not fall back to another owner's retained helper when the selected one is missing. The standalone installer does not regenerate Decky's wrapper, so plugin startup refreshes a wrapper whose helper no longer matches the selected owner. Legacy identity readers and their removal gates remain in [CLEANUPS.md](CLEANUPS.md).

Packaged Decky metadata and each new active native identity include `payload_sha256hash`, the SHA-256 of the archive's `MAKO-Renderer-install-manifest.txt` bytes before desktop rewriting. Package validation and installation check that fingerprint against the embedded archive. Decky compares it across both installer owners, so same-version rebuilds and bundled MAKO FG changes are visible. A record cannot see files replaced outside Decky or left by an interrupted install, so when Decky's own identity matches, `check_installation()` also compares the installed layer libraries and MAKO FG files, which are copied verbatim, with the bundled manifest's per-file checksums. It reads that manifest once per plugin process, trusts it only when it matches the fingerprint, and rehashes an installed file only when its size, modification time or inode changes; generated and rewritten files are not compared. Installed Flatpak runtime branches are checked the same way against `flatpak-runtimes.json`: one MAKO Decky did not install, whose commit changed, or whose bundle the plugin no longer carries also offers the update, whose Flatpak refresh resolves it. Equal native manifests remain equal despite different archive compression or local package version labels. Legacy packages without this field retain the older version/archive comparison; a new package offers an update when an older standalone identity lacks the fingerprint.

### Lifecycle and package boundaries

| Action | Result |
| --- | --- |
| Remove or reinstall MAKO Decky | Stop Decky workers; retain native Renderer, its selected owner, self-contained launcher, Remote Play override, profiles, and shared Flatpak extensions. Reinstallation discovers the existing selection. |
| Install a newer Decky ZIP | Replace the plugin; offer a native update when its bundled payload, an installed layer or MAKO FG file, or an installed Flatpak runtime differs. Native replacement remains an explicit action, including when it would replace a newer standalone version with Decky's bundled version. |
| Select **Uninstall MAKO Renderer** or run the user-local uninstaller | Restore native Remote Play first, then remove both managed user-local payloads and their registrations. Keep profiles and shared Flatpak extensions. |
| Install through Decky | Install the native uninstaller, its desktop entry, and the standalone Remote Play restoration command/modules alongside the layers. Those tools remain usable after the plugin is removed. The Decky package also carries current removal scripts under `bin/renderer-management/`, copied from Renderer-owned sources at packaging time. Installation and startup repair those scripts under the native lock and rollback without changing selected layer bytes or package identity; an unchanged startup check creates no backup files, including when a plugin-only package pins an older native archive. Older plugin packages can bootstrap missing scripts from their verified native archive when it supplies the complete set. |
| Install or remove `mako-renderer-bin` | Pacman exclusively owns `/usr`; user-local uninstallers never remove those files. Decky cannot adopt the package. Decky setup reports the separate system owner before an explicit user-local installation; it does not require removing the system package. Keep versions aligned when both use the same profiles. |

Explicit uninstall preserves checksum-modified standalone files, including shared destinations while standalone is selected. Both uninstallers resolve the private layer manifest to select the owner; stale active-state metadata cannot authorize removal of a modified standalone file. When Decky is selected, its known shared destinations belong to the Decky payload rather than the older standalone checksum ledger. Configuration, shader edits, captures, logs, the licensed DLL, and Flatpak extensions remain outside automatic native cleanup. Each Renderer payload installs MAKO FG's separate program and model as managed files, so they need no separate model-directory cleanup.

Direct development deployment uses the same manifest resolver to update the selected native owner and verify the libraries actually selected by private and registered manifests. Its 64-bit CLI, shader tool, and VRR helper follow that selected owner too. It retains package identity and standalone ownership records as the release baseline; local build hashes belong to the development status record. The direct deployment script also writes a plugin-local `bin/development-renderer.json` receipt after verifying the copied libraries and MAKO FG files. The receipt binds exact destination checksums to the plugin package and active identity; only a local development backend accepts those specific differences from the bundle. It does not rewrite release ownership, disable file checks, or exempt untouched architectures or Flatpak runtimes. A normal reinstall remains valid against the bundled checksums even if an old receipt remains. See [Direct SteamOS iteration](plugin/docs/PACKAGING.md#direct-steamos-iteration) for the architecture scope and verification contract.

Every native uninstaller removes its managed payload files subject to modified-file preservation, prunes the managed subdirectories they leave empty, and removes an empty `~/.local/lib32` multilib root. It keeps the standard per-user `~/.local/bin`, `~/.local/lib`, and `~/.local/share` roots, which login `PATH` setup and other software rely on. A custom standalone prefix belongs entirely to that payload, so its uninstaller also removes the prefix's empty `bin`, `lib`, and `share` directories.

Standalone `MAKO_INSTALL_PREFIX` relocates its payload and state together. Decky's coexistence logic targets the default `~/.local` installation. Do not assume a custom standalone prefix is adopted by Decky.

## MAKO Decky sequence

1. `install()` reads `package.json` through `_bundled_archive_metadata()`: either `bundled_renderer` or exactly one `remote_binary`, never both. It checks native host compatibility, archive existence and the archive SHA-256 before creating payload directories. Acquiring the native lock can create its prefix and retained lock file. Native AArch64/Armada remains subject to [ARMADA.md](plugin/docs/ARMADA.md).
2. `_ensure_directories()` prepares the destinations. `managed_install_transaction()` snapshots the deduplicated `_decky_renderer_files() + [config_file_path]` set before entering the installation body. A destination must be absent, a regular file, or a symlink; other existing types abort preparation.
3. `_extract_and_install_files()` stages selected regular archive members under `.mako-install-*` in MAKO's user-owned data directory. It maps recognized layer and shader-catalog paths to fixed destinations and recognizes the optional CLI by basename; it does not extract arbitrary archive paths into the installation. The required 64-bit FG/scaling chain and complete shader catalog must exist. The optional 32-bit chain must be complete or absent. Layer role and profile-fallback build markers are validated before the replacement loop.
4. That loop normalizes layer JSON and replaces binaries/manifests through the managed-file helpers. JSON parsing/normalization occurs in the loop, so a malformed later manifest can fail after earlier replacements and require rollback. A 64-bit-only local payload removes stale managed 32-bit layer files.
5. `_register_layer_manifests()` installs gated discovery manifests, removes stale 32-bit registration when absent, and retires the standalone archive's public spatial-scaling registrations. The Gamescope WSI and guarded postprocess helpers refresh their managed files. An unavailable or invalid optional host integration removes its managed copy and leaves that integration unavailable; this alone is not a native-install failure. Filesystem errors that escape those helpers trigger rollback.
6. `_create_config_file()` preserves and merges valid profiles with current defaults. An unreadable/unparseable/invalid configuration, including an unsupported version, falls back to defaults; a file with no write bits is explicitly rejected before that fallback. The canonical schema removes unknown keys on serialization. Because `conf.toml` is in the transaction, a later install failure restores the original file even after a default fallback.
7. `_create_mako_launch_script()` rebuilds `mako-run` from the resulting configuration and existing sidecar reads. `_install_diagnostics_helper()` installs the packaged helper. Wrapper/profile sidecars are not installation outputs and are not in this rollback set.
8. `_write_engine_state()` writes the Decky payload record; `_write_active_renderer_state()` writes the selected Decky identity last. Normal context exit discards backups and `install()` reports success. Exceptions cause restoration before the service returns its failure response; non-`Exception` failures are re-raised after context cleanup.

`InstallationService._renderer_file_inventory()` is the Decky file-set owner: archive extraction and installed-payload checks consume its required and optional mappings, while rollback and uninstall consume all of its managed paths. It includes both layer chains, private and registered manifests, the retired standalone public spatial-scaling registrations, managed Gamescope/MangoHud/vkBasalt files, the packaged vkBasalt shader catalog, the required Gamescope VRR lease helper, the optional CLI, native uninstaller/desktop entry and Remote Play command/modules, both identity records, `mako-run`, and `mako-diagnostics`. Add any new file written or removed by the installation body to that inventory before relying on rollback. The standalone installer remains independently deployed and keeps its own native cleanup list; a cross-component test requires that list to match Decky's inventory. Standalone binaries and its ownership manifest are outside the Decky set; shared entries overwritten by Decky are inside it. Keeping the packaged catalog under `~/.local/share/mako-render/vkbasalt-shaders/` also preserves configs written by older Qt builds, while current Decky and Qt saves use the canonical per-user copies under `~/.config/mako-render/vkbasalt/shaders/`.

### File replacement and backup mechanics

`_create_staged_file()` creates an exclusive random sibling with `O_CREAT | O_EXCL` and the requested mode, plus `O_CLOEXEC` when available. Requested modes are normally `0644` for data and `0755` for executables. A restrictive umask is retained when required owner bits survive; if owner bits are missing, `fchmod()` attempts to restore the requested mode and failure aborts the write.

The copy/text helpers finish writing, flush and fsync the staged file, close it, then replace the destination entry. The text helper optionally assigns ownership to the staged file before publication and checks a caller-supplied destination guard immediately before rename; ownership or guard failure leaves the destination unchanged. An existing destination symlink is replaced without writing through it. Parent directories must permit creation and rename even when the old managed file itself is read-only. `write_managed_text_atomically()` skips replacement when content matches, required owner bits match, and the existing regular file has no permissions outside the requested mode; private umasks therefore do not cause repeated rewrites. A specified owner must also match before skipping replacement.

For each existing transaction path, `managed_install_transaction()` allocates an adjacent `.mako-rollback-*` directory. A regular file is hard-linked into it, with a copy fallback; a symlink is backed up as a symlink. An absent path is recorded without a backup file. All callers must replace existing inodes rather than edit them in place, because an in-place write would also change a hard-linked backup.

On failure, the helper restores backups with `Path.replace()` in reverse path order and unlinks paths that were originally absent. An optional rollback guard preserves an externally changed destination and retains its available recovery snapshot instead of restoring over it; the transaction reports this incomplete rollback. It attempts every restoration even if one fails. A failed restoration retains its available backup and raises an `OSError` containing the original error, restoration failures and retained directories. Backup cleanup failures are warnings and do not reverse a successful install.

## Native Remote Play override

This is a separate, opt-in Steam transaction, not an additional Renderer payload destination. `engine/scripts/mako_remote_play/remote_play_core.py` owns Steam's native x86_64 `streaming_client`, its `.mako-original` backup and `.mako-original.sha256` checksum, and `~/.config/mako-render/native-remote-play.json`. `Plugin` snapshots those four paths together with `conf.toml`, profile metadata, wrapper sidecars, and `mako-run` before refreshing the existing launcher and installing the wrapper. A failed Decky installation restores existing canonical data, including AC/battery tables. Qt flushes pending edits through its existing writer, then invokes the shared command asynchronously. The shared owner seeds `vkbasalt/current-profile.conf` beside the installed TOML configuration before exposing the wrapper and rolls back this replaceable selected-shader cache together with its Steam paths in either case. A failed removal restores the four Steam override paths except a client observed to have changed outside the transaction; that client is preserved and the available snapshot is retained for manual recovery. Profiles are not created or rewritten by override installation; existing canonical per-profile shader configurations are outside this transaction. Decky ordinary profile selection snapshots the TOML key, launcher, and selected-shader cache together so a failed launcher refresh restores the old selection and shader content.

A nonblocking exclusive lease rejects mutations during a stream or another mutation. The self-contained launch payload keeps a shared lease across the exec chain; exact executable detection also guards streams launched before installation. Native ELF identity, executable mode, user ownership, checksum, and symlink checks precede replacement. An intact installed wrapper is idempotent. After launcher migrations, plugin startup and Qt refresh update changed packaged payload content only for an existing intact enabled override, using the verified original's ownership and permissions; it defers during a stream and retains profiles/power tables. The actual system Python interpreter is checked before installation or refresh. Installation refuses existing experimental overrides; it does not adopt their backups. These locks coordinate MAKO actions, not Steam's updater. Hash checks detect a client change during preparation, but cannot provide an atomic transaction with a concurrent Steam update; close streams and avoid concurrent Steam updates.

Removal checks the stored wrapper hash and original checksum. It restores the original only when the managed wrapper remains installed. If Steam already replaced it with a native client, removal retires the stale backup and state without overwriting that client. Explicit Decky Renderer uninstall restores the override before cleanup, preserving Renderer files on restoration failure. Decky plugin removal preserves the self-contained override together with its native Renderer and launcher. The standalone archive uninstaller invokes the shared restoration command before removing payloads or configuration and stops on failure. An older install without that command refuses cleanup when override bookkeeping or backups exist. System-package removal and manual deletion require prior UI restoration. Missing configuration or launch dependencies cause verified native passthrough, while missing/corrupt original bytes stop launch. Unlike the generic native payload transaction, Remote Play explicitly syncs recovery files and their parent directories before publishing the wrapper, and syncs native restoration before removing bookkeeping. It can restore an exactly known current wrapper with missing/corrupt state if its original checksum verifies, and can clean up interrupted removal after a native client is already present without replacing it. Regular-file checks reject redirected/special launch records without blocking. The per-file atomicity and termination limits described above still apply; there is no durable multi-file recovery journal. The lock file is retained as a stable synchronization inode after removal.

## Standalone sequence

1. `install_payload()` acquires the native lock, then checks for the packaged manifest/version, warns if Decky is installed, validates the version and relative-path/hash syntax of the new manifest and any existing ownership manifest, and obtains the installer's normal confirmation.
2. It installs `EXIT`, `HUP`, `INT`, and `TERM` traps and stages under `$install_prefix/.mako-install-*`. Every manifest entry is copied with preserved mode and checked against its SHA-256 before any selected destination is replaced.
3. Desktop `Exec` paths are rewritten in staging. The active identity fingerprints the original native payload manifest. The installer computes `installed-files.sha256` from the rewritten staged content and creates the standalone `active-renderer.json` there.
4. `prepare_install_destination()` prepares every payload destination with an adjacent `.mako-install-*` directory containing `previous` when the destination existed and `replacement` when new content will be installed. Previous symlinks are copied as links. This finishes for all destinations before `install_replacing=1`.
5. An old ownership entry absent from the new manifest is scheduled for removal only when its current file still matches the old hash. Modified obsolete files are preserved. Current payload paths are replacement targets even if their previous contents were modified. The ownership manifest and active identity are prepared last, in that order.
6. After `install_replacing=1`, the destination loop performs `mv -fT` for replacements and `rm -f` for scheduled removals. Only after the complete loop does it set `install_committed=1` and invoke `finish_install()` to discard staging/backups and remove traps.
7. Release the native installation lock after commit, before completion notification and optional `mako-ui` startup. A configuration-app startup failure is reported separately and does not roll back the installed Renderer.

Before replacement starts, failure only needs staging cleanup. During replacement, `finish_install()` restores every prepared destination in reverse order from `previous`, or removes it if originally absent. Restoration failures retain available `previous` backups beside the destination and report their locations; a failure removing an originally absent path has no previous file to retain. The installer returns failure when the native transaction fails.

## Boundaries outside the transaction

- `Plugin.install_mako()` refreshes already installed Flatpak extensions only after native installation succeeds. A reported refresh failure leaves native success intact and adds `flatpak_refresh_error`; individual runtime updates are not rolled back with the native files. [Flatpak preparation](engine/docs/FLATPAK-GUIDE.md) is a separate boundary.
- Decky Loader's ZIP installation, plugin startup repairs, profile-edit transactions, direct development deployment, manual archive extraction, `cmake --install`, and native uninstallation do not pass through these complete native-install transactions. An atomic helper used by one of those paths does not imply the surrounding operation has this rollback contract.
- Configuration/profile sidecars, diagnostics history, installed Flatpak extensions, the plugin itself, and the licensed `Lossless.dll` are outside the native payload rollback set. Decky's `conf.toml` exception is described above; standalone configuration removal is an explicit uninstall option.
- Adjacent backup naming supports error reporting and manual recovery, not automatic replay. There is no persistent operation journal or startup scan that can safely infer and complete an interrupted installation from leftover directories. Preserve reported backups when investigating restoration failures.
