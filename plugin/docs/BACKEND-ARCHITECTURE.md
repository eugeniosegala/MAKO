# MAKO Decky backend code map

MAKO Decky's Python backend translates UI requests into canonical profile data, generated launch wrappers, installed files, and runtime status. The modules have distinct ownership even where a service orchestrator remains large.

| Concern | Owner | Boundary |
| --- | --- | --- |
| Async RPC and Decky lifecycle | `py_modules/mako_plugin/plugin.py` | Validates request shape, calls services, and returns typed responses; it does not own profile serialization or file replacement. |
| Public response mappings | `py_modules/mako_plugin/types.py` and owning service types | Keep Python RPC payloads aligned with `src/api/makoApi.ts` and the RPC contract tests. |
| Renderer TOML and profile transactions | `py_modules/mako_plugin/configuration.py` | Orchestrates profile and wrapper-sidecar changes, locks configuration field writes, and regenerates dependent files. |
| Profile metadata and wrapper sidecars | `py_modules/mako_plugin/profile_storage.py` | Normalizes persisted Decky-only values and owns profile identity, vkBasalt content merging, FX discovery, and pure file-reference registration. `ConfigurationService.add_profile_shader()` validates the profile and writes its file atomically under the existing configuration lock; FX source files remain external. |
| Pure launcher generation | `py_modules/mako_plugin/wrapper_generation.py` | Emits the current wrapper format from normalized inputs; no runtime import from MAKO Renderer. |
| Atomic replacement and rollback | Generated `py_modules/mako_plugin/managed_files.py` from `engine/scripts/mako_remote_play/managed_files.py`, and `installation.py` | The shared helper owns file primitives; Decky installation owns the native payload transaction and selected Renderer identity. |
| Flatpak setup | `py_modules/mako_plugin/flatpak_service.py` | Detects runtime extensions, records what it installs into each branch in `flatpak-runtimes.json`, reports branches that differ from the bundle, and manages application overrides outside the native installation transaction. |
| Native Remote Play override | `py_modules/mako_plugin/remote_play.py`, with generated `remote_play_core.py` and `remote_play_launch.py` from `engine/scripts/mako_remote_play/` | The thin Decky adapter supplies paths and typed RPC responses. One shared owner handles Steam installation, recovery, and detection; existing launchers and Renderer retain feature/power policy. |
| Runtime status | `py_modules/mako_plugin/runtime_state.py` | Validates and reads MAKO Renderer's atomic status records; it does not apply profile changes. |
| Paths and stable identifiers | `py_modules/mako_plugin/base_service.py`, `constants.py`, and `package_paths.py` | Resolve the Decky user's paths, packaged payloads, and compatibility names. |

`config_schema.py` preserves and normalizes the Renderer's optional per-profile `handheld` and `docked` TOML tables through capture, clone, rename, selection, deletion, and installation. Mode-aware field patches keep native settings isolated while writing globals and wrapper settings to their existing shared owners. `host_environment.py` reports power for editor selection only; the Renderer independently owns actual startup and live selection. `wrapper_generation.py` retains layer discovery for every saved power set, leaving actual resource provisioning to the Renderer. Focused power-profile tests and RPC contracts guard this independently deployed boundary.

`shared_config.py` owns the cross-language configuration schema. Generate its Python and TypeScript bindings through the owning script; never edit generated bindings directly. A profile write must keep Renderer TOML, Decky sidecars, the selected shader configuration, and the generated wrapper coherent. `InstallationService._renderer_file_inventory()` owns archive destinations and the file set used for native rollback and cleanup; the standalone installer's independent cleanup list must match it through the cross-component test. Installation and Flatpak preparation are separate transactions with the limits recorded in [native installation transactions](../../INSTALLATION-TRANSACTIONS.md).

Native base and power-table serialization derives its field set from that schema's `toml`/`profile` locations, excluding the shared process match. Adding a native setting does not require another Decky writer or power-mode mapping. The power-profile contract checks every schema-owned native key in both tables; shader and launcher sidecars remain shared across power modes.

Keep orchestration in `ConfigurationService` and `InstallationService` when an operation must coordinate several files. A shorter file is not a reason to create a second state owner or to move only half of a transaction. Follow [testing](../../TESTING.md) and the focused backend contract tests whenever an RPC, profile, wrapper, installation, or Flatpak boundary changes.

`FlatpakService.get_flatpak_apps()` reads each app's current compatible Freedesktop Vulkan-layer branch through the same detector used by preparation, including inherited KDE/GNOME runtime metadata. Its required nullable `runtime_version` field is independent of saved override state; null means the runtime is unsupported or could not be determined. The inventory RPC runs off the async event loop. Inventory reads never rewrite preparation or install extensions; Renderer installation refreshes only already installed branches.

`process_detection.py` owns Decky's process-alias eligibility, including generic launch/browser helpers and the generated shared Windows launcher exclusions. For Wine/Proton it follows the Renderer's primary mapped executable authority before considering thread names or command-line arguments, so an excluded launcher's mutable thread name or future game argument cannot resurrect it during capture. Capture and `wrapper_generation.py` reuse the alias policy so older launcher/helper aliases cannot select another game's profile through command-line matching. The current wrapper format regenerates older caches without rewriting saved profiles; recapture replaces their previous automatic aliases while preserving manual matches.

Steam process ownership also recognizes UMU's `UMU_STEAM_GAME_ID`, which preserves the original Steam game ID when Heroic/UMU replaces the ordinary Steam variables with its compatibility identity. Shortcut matching compares the complete packed game ID against the requested unsigned AppID; ordinary Steam games use their direct ID. The normal executable and launcher exclusions still apply. This allows capture and automatic profile selection to find the actual game without counting Heroic, UMU, or a prelauncher as a running game.

`ConfigurationService.delete_profile_shaders()` removes only requested, currently selected custom registrations through `profile_storage` and the normal field-patch writer under the configuration lock. It reuses `managed_install_transaction()` for rollback of the touched profile configuration, shader files, sidecar, and generated wrapper if persistence fails; this is a profile edit, not a native installation. External FX files remain untouched. The frontend drains its existing save queue before deletion, locks effect selection while the action runs, and reloads the current editor power set afterward.

## Flatpak VRR discovery lifecycle

`plugin.py` starts and stops the selected native Renderer's `mako-vrr-lease --watch-flatpak` host monitor on plugin load/unload and Renderer install/uninstall. `InstallationService.selected_vrr_lease_file()` and the wrapper's `renderer_bin_dir` map the private manifest's owner to Decky's or the standalone archive's helper, so both use the helper version that matches the selected Renderer. The helper owns bounded runtime-status discovery, namespace process validation, compositor verification, and detached game leases. Decky does not implement a second VRR writer; detached leases survive plugin reload to preserve exit restoration. Missing helpers or a different user identity leave discovery disabled.

Decky Loader 3.3.1 stops a plugin by sending SIGTERM, closing the plugin socket, and sending SIGKILL five seconds later. After that socket closes, Loader's in-plugin listener can monopolize the event loop. `_unload` and `_uninstall` therefore finish without suspending: an awaited step would never resume, and its timeouts would never fire. They SIGKILL the monitor without waiting, because discovery owns no VRR state and init reaps it after the backend exits. They also cancel the frame-recording shortcut watch without awaiting it, and `_uninstall` runs its cleanup inline. The monitor also receives this backend's PID in `MAKO_VRR_WATCH_PARENT` and exits on its own when the backend dies, which covers a Loader that kills the backend before either hook runs. Do not rely on systemd for this: `plugin_loader.service` uses `KillMode=process`, so stopping or restarting Loader leaves the monitor in its cgroup. Renderer installation and uninstallation requests stop discovery gracefully instead: two seconds for termination, then one second to reap the killed monitor. If the killed monitor still has no exit status, Decky logs the failure and retains its process handle to prevent duplicate discovery until exit is observed. Only that monitor is signalled; detached game leases remain responsible for VRR restoration.

## Native Remote Play lifecycle

`Plugin` coordinates the existing launcher writer and `RemotePlayService.install_locked()` under the configuration lock, a native-client launch lease, and one explicit file snapshot. Existing profiles and power tables survive reinstall; installation creates no profiles and does not change feature settings. Status and mutation RPCs run filesystem/process work off the async event loop. Uninstalled status avoids process and Renderer-status scanning. The wrapper inherits its shared lease through the exec chain, preserving installation/removal exclusion during launch preparation and the stream lifetime. Plugin startup refreshes only an already enabled, intact launch payload after canonical launcher migrations, retaining the original/profile and deferring during a stream. Remote Play reuses the managed-file owner's staged ownership and replacement/rollback guards; its ordered directory syncs prepare recovery dependencies before exposing the wrapper. Detected foreign Steam replacements are preserved during rollback. Explicit Decky Renderer uninstall acquires the native installation lock, then restores the Steam entry point before removing files; failed restoration preserves Renderer files. RPC cancellation retains the native lease until an ongoing restoration worker finishes, then leaves Renderer files installed. Removing the Decky plugin preserves the independent Renderer and override. See [Remote Play](REMOTE-PLAY.md) and [transaction boundaries](../../INSTALLATION-TRANSACTIONS.md#native-remote-play-override).

Qt invokes the packaged `mako-remote-play` command asynchronously instead of implementing Steam replacement in C++. The binding generator makes Decky self-contained with byte-identical policy modules and no Renderer runtime import. Current override state preserves the installing launcher/configuration across refreshes. No earlier override-version migration or dedicated-profile path is supported. Remote Play launch reads current discovery and shared shader inputs so Qt edits do not require cached `mako-run` regeneration. Confirmed remote-session synchronization reads the latest canonical selection under the configuration lock, so a delayed detection reply cannot restore the previous profile after creation. Decky and Qt refresh the replaceable `vkbasalt/current-profile.conf` cache from ordinary canonical shader files when saving or selecting; selection rollback includes this cache and the normal launcher. Alternate Qt configurations are reported as conflicts in Decky, preventing incorrect automatic profile following or preparation.

Manual and automatic profile selection use the same configuration write lock and managed-file transaction for the selected TOML key and generated launcher. A launcher refresh failure restores the previous files and returns an error instead of reporting a successful selection.

## Shader configuration and parameters

For an uncaptured Steam game using Default shaders, `wrapper_generation.py` reserves its ordinary `vkbasalt/steam-<app-id>.conf` filename with a non-replacing symlink to the global Default file. Default edits remain live through that link. Profile capture atomically replaces the link with the cloned shader content, or moves an adopted manual profile's file over it, so vkBasalt keeps watching the same filename. Cleanup retains these Default aliases until capture; they contain no unique settings. Other games, explicit profile overrides, and the Remote Play selection cache remain independent. Existing wrappers regenerate through the normal format gate; games already launched with an older wrapper need one restart.

`ConfigurationService.reload_profile_shaders()` advances `makoReloadGeneration` in the selected vkBasalt file under the existing configuration lock and returns the normal catalog response. Refresh drains the frontend save queue first. Qt uses its independent `reloadVkBasaltConfiguration()` owner after a successful pending save. The bounded generation is reserved from custom aliases, preserved by ordinary configuration merges, and forces the dependency to rebuild unchanged selections after source/include/texture edits; it adds no source-file polling or Renderer profile field.

Shader customization uses `shader_parameters.py` to invoke the installed `mako-shader-tool` in a bounded subprocess and validate its typed metadata. The child restores `LD_LIBRARY_PATH_ORIG` when supplied, otherwise clears `LD_LIBRARY_PATH`, so Decky’s PyInstaller libraries cannot override the native helper’s host dependencies; the plugin process environment remains unchanged. That helper belongs to the maintained vkBasalt payload and uses its runtime ReShade preprocessor/compiler, including shader includes and annotations. The configuration service caches only the open editor’s metadata and exact config content; `profile_storage.py` merges validated effect-local assignments. Atomic profile/cache writes use the existing rollback transaction. Copies, renames, deletion, and power-mode sharing retain the existing shader-file lifecycle. The public RPCs run this work outside the async plugin event loop. Discovery releases the profile write lock during compilation, then revalidates profile identity and configuration content before returning controls. The helper is optional only for installing older Renderer archives; such archives cannot enable the new editor, and installation removes any stale private helper on downgrade.

Native Renderer removal is explicit. Decky Loader removal stops plugin workers and preserves the selected native payload, self-contained launchers, profiles, and Remote Play override. `installation.py` owns the shared native install/uninstall lock and payload fingerprints; `development_renderer.py` shares the direct-deployment receipt reader/writer with the deployment script, binding verified native copies to the current plugin package and active identity so local builds do not offer a misleading bundled update; `BaseService._selected_renderer_bin_dir()` routes model/shader tools and wrapper helpers to the same manifest-selected owner. Unchanged startup checks create no backup snapshots. The independently installed native uninstaller remains usable without Decky. The installation-status RPC exposes a nullable `system_renderer_notice` for separate pacman ownership; it is informational and does not block an explicit local installation. See the [lifecycle matrix](../../INSTALLATION-TRANSACTIONS.md#lifecycle-and-package-boundaries) for pacman and Flatpak boundaries.
