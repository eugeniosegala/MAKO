# Native Steam Remote Play

MAKO Decky can explicitly wrap the receiving device's native Steam streaming client so it launches through the existing MAKO Renderer configuration path. This integration is disabled until the user selects **Override Remote Play**. Installation/removal controls belong to Decky; the dedicated process profile uses the same Renderer configuration as the standalone Qt editor. It does not introduce a video decoder, a frame-generation algorithm, or a separate live-settings policy.

## Contribution review

[Issue #74](https://github.com/eugeniosegala/MAKO/issues/74) contains hugouchoasborges's native-client wrapper proof of concept, reports, demonstration links, an alternative Vulkan meta-layer experiment, and a later Decky integration patch. The contributor reports successful native Steam streams on their Deck. Their standalone Steam Link experiments encountered OpenGL ES/Zink problems; their meta-layer experiment increased an FPS counter without convincing visible interpolation. Those reports motivate the native wrapper approach, but are not independent MAKO hardware qualification or proof of why the approaches differ.

The integration patch was reviewed as text and adapted to the current owners rather than applied or executed wholesale. Its Steam entry-point replacement, dedicated profile, explicit opt-in, restoration, exact-process detection, and runtime indicator are retained. The adapted implementation removes separate Base-only frame-generation/resource preflight in the entry script: `mako-run` and the Renderer remain responsible for all saved feature settings, AC/battery selection, model availability, WSI preparation, and supported live transitions. This also retains the normal launch path for MAKO Scaler and Shaders without Lossless Scaling.

The adapted implementation adds stale-poll rejection, save-queue draining, typed RPC contracts, canonical-profile rollback, backup and wrapper integrity checks, an inherited launch lease, removal guards, Steam-update preservation, and focused portable tests. It does not install the contributor's binaries, use the experimental meta-layer, alter global Zink settings, or copy their hardware evidence into the repository.

## State and launch flow

1. Installation verifies the native executable, refuses preexisting experimental state, snapshots the explicit Steam and canonical configuration files, and creates the process profile only if absent. Its stable internal name is `Remote-Play`, with **Remote Play** as the Decky display name. The initial settings are Fixed 2x, 30 FPS base cap, and 60 FPS target; separate power settings remain off by default.
2. Steam launches the self-contained Python 3.11+ script at its usual `ubuntu12_64/streaming_client` entry point. Its original is `streaming_client.mako-original`, with an adjacent SHA-256 file. The wrapper verifies that original before execution and keeps a shared launch lease through `mako-run` and the native client.
3. The wrapper selects `Remote-Play` through `MAKO_PROFILE`, passes Steam's arguments unchanged, and delegates setup to `mako-run`. It removes inherited MAKO activation and Zink exports; the native client receives no Zink driver override even if the profile's generic launcher option enables it. Configuration and feature preparation remain owned by the normal launcher and Renderer.
4. Decky recognizes the exact executable path, including deleted executable inodes and the short Python entry phase. It follows the dedicated profile without requiring an AppID or creating a local-game capture. Existing queued writes, power-source reloads, live edits, restart markers, and runtime status remain in their existing owners.
5. Removal verifies original and wrapper integrity, restoring the original only while MAKO's unchanged wrapper is installed. If Steam has already installed a native replacement, removal preserves it and retires the old backup/state. The saved profile remains. Closing a stream does not remove the global override.

`~/.config/mako-render/native-remote-play.json` records version 1, the enabled flag, profile identity, and wrapper SHA-256. Its lock is `native-remote-play.lock`; retain that inode after removal to avoid replacing a synchronization object held by another process. The script is self-contained so it does not import a deleted or reloaded plugin. Existing wrapper payloads remain installed until explicit removal/reinstallation; changing their contract requires considering installed version-1 state and integrity checks.

## Recovery and limits

Missing or malformed configuration/state, missing `mako-run`, failure to execute the runner, or a missing launch lease yields checksum-verified native passthrough with MAKO and its spatial layer disabled. Missing or altered original bytes stop launch. Passthrough cannot recover a failure after successful execution has transferred to the runner or native client.

The override is a separate Decky transaction using the existing managed-file primitives. It provides per-file atomic replacement and exception rollback, not durable recovery after power loss or coordination with Steam's updater. Do not update Steam concurrently with installation/removal. Decky Renderer/plugin uninstall restores the override before cleanup and preserves Renderer files if restoration is blocked. Standalone uninstall does not restore this Decky entry point; remove the override through Decky first. If standalone cleanup already removed configuration/dependencies, the verified original can still launch through passthrough. Corrupted backups or unfamiliar wrapper changes require manual recovery rather than automatic overwrite.

The current integration targets the usual native x86_64 Steam install, not Flatpak Steam, standalone Steam Link, browser streaming, or AArch64. Portable tests validate file safety, launcher delegation, profile behavior, and UI state. Real native Remote Play streams still need independent qualification for visible interpolation, decoding, output cadence, image quality, input latency, host/client combinations, and Gamescope/Desktop behavior. An active Renderer context confirms its reported state; it is not a measurement of physical display output.
