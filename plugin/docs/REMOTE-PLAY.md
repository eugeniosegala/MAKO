# Native Steam Remote Play

MAKO Decky and the standalone Qt configuration app can explicitly wrap the receiving device's native Steam streaming client so it launches through the existing MAKO Renderer configuration path. The override starts disabled. Select **Override Remote Play** on the receiving device to enable it; Qt also offers **Refresh** and **Restore Steam Client**. Both UIs manage one override; each stream uses the ordinary profile selected before launch. They use existing configuration writers, launchers, and Renderer live-setting policy.

## Contribution review

[Hugo Uchôas Borges (@hugouchoasborges)](https://github.com/hugouchoasborges) contributed the native-client wrapper proof of concept and Decky integration patch adapted into MAKO's Remote Play support, along with reports, demonstration links, and an alternative Vulkan meta-layer experiment in [issue #74](https://github.com/eugeniosegala/MAKO/issues/74). The contributor reports successful native Steam streams on their Deck. Their standalone Steam Link experiments encountered OpenGL ES/Zink problems; their meta-layer experiment increased an FPS counter without convincing visible interpolation. Those reports motivate the native wrapper approach, but are not independent MAKO hardware qualification or proof of why the approaches differ.

The integration patch was reviewed as text and adapted to the current owners rather than applied or executed wholesale. Its Steam entry-point replacement, explicit opt-in, restoration, exact-process detection, and runtime indicator are retained. The adapted implementation removes separate Base-only frame-generation/resource preflight in the entry script: the existing launchers and Renderer remain responsible for all saved feature settings, AC/battery selection, model availability, WSI preparation, and supported live transitions. This also retains the normal launch path for MAKO Scaler and Shaders without Lossless Scaling.

The adapted implementation adds stale-poll rejection, save-queue draining, typed RPC contracts, launcher rollback, backup and wrapper integrity checks, an inherited launch lease, removal guards, Steam-update preservation, and focused portable tests. It does not install the contributor's binaries, use the experimental meta-layer, alter global Zink settings, or copy their hardware evidence into the repository.

## State and launch flow

1. Select or create an ordinary profile and save its settings before streaming. Installation verifies the native executable, supported launcher, and actual system Python interpreter, refusing preexisting experimental state. Decky snapshots Steam and canonical configuration files together before refreshing its existing launcher. Qt saves pending edits through its existing writer before invoking the shared helper. Enabling or removing the override creates, deletes, or rewrites no profiles.
2. Steam launches the self-contained Python 3.11+ script at its usual `ubuntu12_64/streaming_client` entry point. Its original is `streaming_client.mako-original`, with an adjacent SHA-256 file. The wrapper verifies that original and retains a shared launch lease through the launcher and native client.
3. The wrapper reads `current_profile` from the installed configuration at launch and passes that initial name through `MAKO_PROFILE`, opts into saved selection changes with `MAKO_FOLLOW_CURRENT_PROFILE=1`, passes the configuration path through `MAKO_CONFIG`, and preserves Steam's arguments. The existing Renderer configuration watcher resolves the saved selection again after edits; normal local games retain their existing process matching. Decky installations use `mako-run`; standalone installations use `mako-launch`. Refreshing an intact override preserves its selected launcher and configuration. It removes inherited MAKO activation, environment-only configuration, and Zink exports; the native client receives no Zink override even if a generic launcher option enables it.
4. At process start, the wrapper reads current native layer-discovery flags across Base, Handheld, and Docked, plus the shared shader/launcher sidecar. Decky's existing generated launcher consumes those discovery inputs only for Remote Play, so a Qt shader edit does not require regenerating `mako-run`. Standalone launch delegates shader activation to `mako-launch`. The Renderer retains all native feature values, model detection, power selection, and live transitions; there is no per-frame wrapper work. Standalone launch keeps its normal WSI and overlay policy rather than adopting Decky-only launcher options.
5. Decky recognizes the exact executable path, including deleted executable inodes and the Python entry phase through Steam aliases or relative script paths. It follows the saved selection without an AppID or local-game capture. During a stream, **Create Profile** drains queued writes, copies the current ordinary profile including both power sets and custom shader registrations, asks for a name, and selects the saved copy. Later edits target that copy; it remains selected on exit and is available for future streams. The existing profile dropdown, rename, and deletion controls stay locked until the stream closes. Selection polling reads canonical state after native detection and rejects replies predating a manual selection. Existing power-source reloads, live edits, restart markers, and runtime status remain in their existing owners. A Qt override using an alternate configuration is reported as a conflict in Decky and is edited in Qt; Decky does not follow or overwrite the unrelated default profile. Qt edits the configuration open in the app; streams use the configuration recorded by the installed override.
6. Removal verifies original and wrapper integrity, restoring the original only while MAKO's unchanged wrapper is installed. If Steam has already installed a native replacement, removal preserves it and retires the old backup/state. All profiles and their power tables remain. Closing a stream does not remove the global override.

The shared Python owner is `engine/scripts/mako_remote_play/`. `generate-remote-play-bindings.py` bundles byte-identical modules into Decky; freshness gates reject stale bindings. The native archive installs the same package and the `mako-remote-play` command, which Qt invokes asynchronously. Installed components never import each other. The command provides `status`, `install`, `remove`, `refresh`, and `restore-before-uninstall`, with `--launcher` and `--config` paths. `status` is read-only; `refresh` updates only an already enabled, intact override. Qt queries/refreshes on opening and on explicit Refresh, with no additional idle polling.

`~/.config/mako-render/native-remote-play.json` records version 3, enabled state, wrapper SHA-256, launcher path, and configuration path. This shared installation record stays under the Steam user's home even when Qt opens another configuration. The adjacent `native-remote-play.lock` inode remains after removal. The launch script is self-contained and does not import either UI. Decky startup refreshes an enabled, intact payload after canonical launcher migrations. Qt refresh uses the same owner. Updates retain the verified native original and saved profile, never enable an uninstalled override, and defer during streams.

This feature has not shipped publicly. Only the current override marker/state is supported; there is no dedicated-profile compatibility or earlier override-version migration. Restore experimental or older branch wrappers using their original tools before enabling the current integration. The selected profile is ordinary configuration data, independent of override installation state. Decky and Qt persist it as the optional root `current_profile` TOML key. Published Decky's `# decky-current-profile = "name"` selection comments remain readable in Decky, Qt, and the launch reader; the next canonical write emits the TOML key. All three prefer a valid root selection, then a valid comment, then Default (`mako`) or the first available profile. Selection does not alter normal local-game process matching. Streams follow saved selections with normal live-setting lifetimes; changing process-start resources or layer membership still requires restarting the stream.

Selection-following clients launch vkBasalt with the stable `vkbasalt/current-profile.conf` filename beside their TOML configuration. This replaceable cache contains the selected profile's shader text; it is not a profile or a persistence owner. Both editors atomically refresh it from the ordinary profile's canonical shader file when saving settings or selecting a profile. The shared installer seeds it before publishing the Steam wrapper and includes it in rollback. Decky selection rollback covers the TOML key, launcher, and cache together. This keeps live shader edits attached to a newly saved profile through vkBasalt's existing reload path without a new runtime watcher. Shader activation and layer membership retain their normal restart requirements.

## Recovery and limits

Missing or malformed configuration/state, redirected or special launch inputs, missing launchers, failure to execute the runner, or a missing launch lease yields checksum-verified native passthrough. Passthrough removes and disables MAKO's managed Renderer, spatial, WSI, shader, and overlay chain while preserving unrelated layers, including Steam's overlay. Missing or altered original bytes stop launch. Passthrough cannot recover a failure after successful execution has transferred to the runner or native client.

The override is a separate shared-owner transaction using the existing managed-file primitives; Decky additionally snapshots its canonical files and launcher refresh. Backup/checksum/state ownership is ready before publishing the wrapper; staged files and the recovery directories are synced in order. Destination checks reject observed client changes immediately before publication, and conditional rollback leaves a detected foreign Steam replacement untouched, retains recovery snapshots, and reports the conflict. These are per-file atomic replacement and exception rollback safeguards, not a durable multi-file recovery journal or coordination with Steam's updater. Do not update Steam concurrently with installation/removal. Decky Renderer/plugin uninstall and the standalone archive uninstaller restore the override before cleanup, preserving Renderer files if restoration is blocked. System-package removal and manual file deletion do not invoke this user-level restoration; restore the Steam client in either UI first. If standalone cleanup already removed configuration/dependencies, the verified original can still launch through passthrough. A missing or corrupt state record can be recovered only when the installed entry exactly matches the current packaged wrapper and the original checksum remains valid. Interrupted removal can retire remaining managed bookkeeping after the native client has already been restored, without replacing that client. Special recovery files are rejected; corrupted backups or unfamiliar wrapper changes require manual recovery rather than automatic overwrite.

The current integration targets the usual native x86_64 Steam install, not Flatpak Steam, standalone Steam Link, browser streaming, or AArch64. Portable tests validate file safety, launcher delegation, profile behavior, and UI state. Real native Remote Play streams still need independent qualification for visible interpolation, decoding, output cadence, image quality, input latency, host/client combinations, and Gamescope/Desktop behavior. An active Renderer context confirms its reported state; it is not a measurement of physical display output.
